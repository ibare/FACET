
# 이름표가 있으면 다시 만들지 않는다

목록의 차례가 `p q r s` 에서 `q r s p` 로 바뀐다. 자리로만 맞춘다면 네 자리 모두 글자가 달라져
네 번 고쳐야 한다. 그런데 각 항목에 **이름표(키)** 가 붙어 있으면 이야기가 달라진다 — 실제
노드 넷은 하나도 다시 만들어지지 않고, 딱 하나만 제자리로 미끄러져 간다.

{facet:keyReorder}

## 이름표 표를 먼저 만든다

옛 목록으로 표를 하나 만든다 — 키가 옛 목록의 몇 번째에 있었는지. `p→0 · q→1 · r→2 · s→3`.
그 뒤로는 새 목록을 왼쪽부터 하나씩 걸으며 이 표에서 옛 노드를 찾는다.

## "이미 놓인 자리보다 뒤인가" 로만 정한다

찾은 노드를 그대로 둘지 옮길지는 자리를 다시 세지 않고 **경계값(lastPlaced) 하나**로 정한다.
지금까지 처리한 자리 중 가장 늦은 옛 자리보다, 지금 찾은 노드의 옛 자리가 **뒤(≥)** 면 그대로
두고 그 경계를 늘린다. **앞(<)** 이면 옮긴다.

1. 새 자리 0 — 키 `q` → 옛 자리 1. 아직 경계가 0 이라 1 ≥ 0, 그대로. 경계 = 1.
2. 새 자리 1 — 키 `r` → 옛 자리 2. 2 ≥ 1, 그대로. 경계 = 2.
3. 새 자리 2 — 키 `s` → 옛 자리 3. 3 ≥ 2, 그대로. 경계 = 3.
4. 새 자리 3 — 키 `p` → 옛 자리 0. 0 < 3, 옮긴다 — 실제 줄의 끝으로 미끄러진다.

끝: 옮김 1 · 제자리 3 · 만듦 0 · 지움 0 · 고침 0. 실제 노드 넷은 걸음이 끝나도 처음 그 노드
그대로다.

## 이 그림이 세운 전제

- **짝짓는 규칙은 React 의 `reconcileChildrenArray` 꼴(lastPlacedIndex)이다.** 가장 긴 오름
  부분열(Vue 3 이 쓰는 LIS 꼴)로 옮김을 고르는 방식도 있는데, 이 데이터에서는 우연히 두 방식의
  옮김 수가 같다(1) — 이 화면은 그 일치를 보여줄 뿐 두 방식이 늘 같다고 말하지 않는다.
- **속성 고침은 이 조각의 주제가 아니다.** 항목은 `li` 하나에 키 = 보이는 글자뿐이라 비교할
  속성이 없다. missing-key-remount 는 반대로 고침만 있고 옮김이 없는 쪽을 보인다.
- **키가 없었다면 어떻게 됐을지도 셈해 둔다** — 자리로만 맞추면 네 자리 모두 글자가 고쳐지고
  옮김은 0 이다. 화면에는 그리지 않고 설명 글에서만 밝힌다.
- 비교와 반영(실제 DOM 조작)을 한 걸음에 합쳐 그린다. 실제 라이브러리는 이 둘을 갈라 비교를
  다 마친 뒤 반영을 한꺼번에 하지만, 여기서는 찾아낸 순간 바로 실제 줄에 반영한 것으로 그린다.
