# 같은 답, 다른 길

같은 SQL 한 문장을 두 차례로 풀어 본다. 한 길은 두 표를 먼저 잇고 나서 부산 고객만 거르고, 다른 길은
고객을 먼저 거르고 나서 잇는다. 끝에서 두 길의 답의 줄이 하나씩 서로 포개진다.

## 무엇을 보나

- **잇고 나서 거르기** — 주문 여덟 줄 × 고객 네 줄을 짝마다 검사해(검사 32) 이은 줄 여덟이 나오고,
  그 여덟을 도시로 거른다(검사 8). 남는 줄은 셋, 검사 합은 40.
- **거르고 나서 잇기** — 고객 넷을 먼저 거르면(검사 4) Ben · Dev 둘이 남고, 주문 여덟 × 고객 둘을
  잇는다(검사 16). 나오는 줄은 셋, 검사 합은 20.
- 두 답 `(102, Ben)` · `(104, Ben)` · `(106, Dev)` 는 줄 순서까지 같다. 포개지지 않는 것은 길마다의 검사 수뿐이다.

## 전제

- 표 · 줄 · 값은 예로 정한 작은 자료다. 실제 데이터베이스가 낸 실행 계획이나 통계가 아니다.
- 조인은 중첩 반복으로 푼다. 바깥은 `orders`(id 차례), 안쪽은 `customers`(id 차례, 거른 뒤라면 거른 것만)이고,
  짝 하나마다 `o.cust_id = c.id` 를 한 번 검사한다. 거르기는 줄 하나마다 `c.city = 'Busan'` 을 한 번 검사한다.
- 일의 단위는 **조건 검사 한 번**이다. 조인 검사와 거르기 검사를 같은 단위로 더한다.
- 두 길 모두 바깥이 `orders` 라 결과 줄은 주문 차례로 나온다. 집합으로서는 순서가 없지만 화면은 이 순서로 보인다.
- 이 조각은 어느 길이 나은지 고르지 않는다. 길을 고르는 일은 비용 모형의 몫이다.
