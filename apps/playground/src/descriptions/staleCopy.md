## 한 곳을 고쳤는데 다른 곳은 옛것

**서버 여럿이 같은 값을 각자 캐시에 들고 있으면, 한 서버에서 값을 고쳐도 다른 서버의 사본은 그대로 남는다.** 그 서버에서 읽는 사람은 옛값을 받는다.

### 무엇이 일어나는가

키 `price:42` 의 DB 값은 100 이고, 서버 `a` · `b` · `c` 가 모두 캐시에 100 을 들고 시작한다. 처음 화면을 넣어 걸음은 여섯이다.

1. 서버 `a` 에서 120 을 쓴다. 새 값은 `a` 의 캐시를 거쳐 DB 로만 올라간다. `b` · `c` 에는 아무것도 가지 않는다 — 이제 한 키에 **서로 다른 값이 둘**(120 과 100) 살아 있다.
2. `a` 에서 읽으면 120 을 받는다. 옛값 읽기는 0.
3. `b` 에서 읽으면 100 을 받는다. DB 는 120 이니 옛값이다.
4. `c` 에서 읽어도 100.
5. `b` 에서 다시 읽어도 100. 사본은 스스로 새로워지지 않는다.

끝에 가면 읽기 넷 가운데 **셋이 옛값**이다. `b` · `c` 의 사본은 마지막까지 100 이다.

### 왜 이렇게 되는가

쓰기가 제 캐시와 DB 만 고치기 때문이다(제 캐시에만 write-through). 다른 서버에 "값이 바뀌었다" 는 알림이 가지 않고, 캐시에 만료도 없으니 옛 사본이 풀릴 길이 없다. 옛값인지는 **돌려준 값이 그때의 DB 값과 다른가**로 가른다.

### 이 조각이 두는 전제

- 사본을 든 것은 앱 서버의 캐시이고, 원본은 DB 하나다. CPU 캐시의 일관성과는 다른 이야기다.
- 읽기는 늘 제 캐시에서 값을 찾는다 (이 차례에서는 사본이 늘 있다).
- 만료(TTL)는 두지 않았다. 시간이 지나 풀리는 쪽은 캐시 만료 조각이, 알림으로 사본을 지우는 쪽은 무효화 조각이 다룬다.
- 쓰기와 다른 요청 사이의 경쟁은 없다 — 차례대로 하나씩 일어난다.

다른 서버에 알렸다면 옛값 읽기 셋은 생기지 않았다. 그 장치가 캐시 무효화다.
