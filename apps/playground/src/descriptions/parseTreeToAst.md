# 파스 나무와 AST

괄호는 나무에 무엇을 남길까. 파서가 문법대로 지은 **파스 나무**에는 글의 모든 토큰이 잎으로 달리고, 규칙을
하나 펼칠 때마다 안쪽 마디가 하나 생긴다. 컴파일러의 뒷단이 쓰는 것은 그 나무가 아니라, 셈에 필요한 것만 남긴
**추상 구문 트리(AST)** 다.

{facet:parseTreeToAst}

## 무엇을 보나

문법은 뺄셈 하나뿐인 장난감 문법이다. 규칙 다섯 줄마다 AST 로 옮기는 규약이 하나씩 붙어 있다.

- `leaf` — `Term → NAME` · `Term → NUM` 마디가 사라지고 잎(토큰)이 그 자리로 오른다
- `pass` — `Expr → Term` 마디가 사라지고 하나뿐인 자식이 오른다
- `paren` — `Term → ( Expr )` 의 괄호 잎 둘을 버리고 가운데가 오른다
- `op` — `Expr → Expr - Term` 의 가운데 `-` 잎이 마디 이름으로 오르고, 양쪽이 그 자식이 된다

한 판은 원시 글과 토큰 열에서 시작해 다 지은 파스 나무를 한 번에 매달고, 규약 하나를 한 걸음으로 삼아
`leaf` → `pass` → `paren` → `op` 차례로 그 규약의 마디를 한꺼번에 걷는다. 끝 걸음에서 AST 로 값을 셈한다.
기본 판 `(a - b) - 1` · 왼쪽 재귀는 걸음 0 을 넣어 **일곱 걸음**이다. 파스 마디 15 개(안쪽 8 · 잎 7, 층 7)가
leaf 에서 12, pass 에서 10, paren 에서 괄호 둘을 버리며 7, op 에서 5 로 줄어 `-(-(a, b), 1)` = 1 이 된다.
괄호가 없는 글은 걸을 paren 마디가 없어 여섯 걸음이다.

## 손잡이

- **괄호** — `a - b - 1` · `(a - b) - 1` · `((a - b)) - 1` 로 괄호를 더하면 파스 나무가 아래로 층을 더
  매단다(마디 11 → 15 → 19). 그러나 왼쪽 재귀 문법에서 셋의 AST 는 마디 다섯으로 똑같고, 앞 판과 같은 자리에
  내려앉는다. 뜻을 바꾸지 않는 괄호는 AST 에 흔적이 없다. `a - (b - 1)` 에서만 안쪽 `-` 가지가 오른쪽으로 옮겨
  붙고 값이 1 에서 3 이 된다 — 뜻을 바꾸는 괄호는 **AST 의 모양**으로 남는다.
- **문법** — 오른쪽 재귀(`Expr → Term - Expr`)로 돌리면 괄호 없는 글의 파스 나무가 왼쪽 아래 대신 오른쪽 아래로
  뻗고, 그 AST 는 `a - (b - 1)` 과 같은 모양 `-(a, -(b, 1))` 이 되어 값이 3 이다. 괄호 없이 결합 방향을 정하는
  것은 문법의 꼴이다. 같은 글을 **우선순위 선언**으로 다른 나무로 가르는 쪽은 LR 파서와 우선순위 완제품이 보인다.

계기는 파스 나무의 마디 수, 지금 나무의 마디 수, paren 걸음에서 버린 괄호 토큰의 누적이다.

## 코드 패널

코드 패널의 함수는 나무를 새로 짓지 않는다. 파스 나무를 전위 차례의 색인 배열(규약 · 자식 셋 · 잎의 값)로 받아
같은 네 규약을 네 갈래로 삼아 **값과 AST 마디 수**를 셈한다. 화면은 나무를 실제로 고쳐 걷고 코드는 다른 길로
같은 답을 내며, 여덟 조합 모두에서 둘은 같다.

## 전제

- `a` = 5 · `b` = 3 은 예로 정한 값이다.
- 문법은 뺄셈 하나와 괄호만 있는 장난감 문법이다.
- 파스 나무는 문법에서 지은 SLR(1) 표로 파싱해 얻었다. 두 문법 모두 충돌이 없고 모호하지 않아, LALR(1) 이나
  LR(1) 로 지어도, 어느 파서로 지어도 나무는 하나다.
