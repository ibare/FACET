## 같은 파일, 다른 이력

main 에서 갈라져 나온 feature 줄기에 커밋 둘을 쌓았다. 이제 그 고침을 main 에 들이고 싶다. 길은 둘이다 —
두 끝을 부모로 삼는 커밋 하나를 새로 만들거나, feature 의 고침을 main 끝 위에 하나씩 다시 얹은 뒤 main
이름표를 그 끝까지 옮기거나. 어느 쪽이든 마지막 파일은 같다. 그런데 커밋 그래프는 다르게 남는다. 무엇이
새로 생기고, 무엇의 해시가 바뀌고, 무엇이 이름을 잃는가.

{facet:rebaseVsMerge}

### 줄기와 이름표

뿌리 쪽에 A(처음) · B(로그인 추가)가 있고, feature 는 B 에서 갈라져 X(단추 추가) · Y(색 고침)를 쌓았다.
main 은 그 사이 새 커밋을 몇 개 더 받았을 수 있다 — 손잡이 **main 의 새 커밋**이 그 수 m 을 0 · 1 · 2 에서
고르고, 새 커밋은 C(DB 추가) · D(캐시 추가) 차례로 붙는다. 커밋은 부모를 가리키고(화살은 새것 → 옛것),
`main` 과 `feature` 는 커밋 하나를 가리키는 이름표일 뿐이다.

커밋 아래 일곱 글자가 해시다. 이 화면의 해시는 **장난감**이다 — 변경 식별자와 부모의 해시만 넣어
FNV-1a 32 비트로 셈한 값의 앞 일곱 자리다(`tree add-button` · `parent e3ad9ac` 같은 줄을 이어 붙인 글).
실제 git 은 SHA-1(또는 SHA-256)에 트리 · 저자 · 시각 · 메시지까지 넣지만, **부모의 해시가 입력에 들어간다**는
점은 같다. 그래서 부모가 바뀌면 해시도 바뀐다.

### 한 판의 걸음

첫 걸음은 두 줄기가 **갈라진 자리**를 찾는다. main 끝에서 첫 부모를 따라 거슬러 간 커밋들 가운데 feature
끝에서 거슬러 가다 처음 닿는 것이 그 자리다(git 의 merge base 와 같은 것 — 여기서는 늘 B). 화면은 거슬러
가는 길을 한 칸씩 걷지 않고 결과만 세운다. 그다음은 손잡이 **합치는 길**에 따라 갈린다.

- **병합** — 부모 둘(main 끝 먼저, feature 끝 다음)을 가진 커밋 M(feature 합침)이 솟는다. 부모 차례는 git 의
  첫 부모(first parent) 규약과 같다. 옛 커밋은 하나도 바뀌지 않고 해시도 그대로다. main 이름표가 M 으로 한 칸
  오른다. m=1 이면 M 의 해시는 `560f75a`, m=2 면 `41f6470` 이다 — 첫 부모가 C 에서 D 로 바뀌었으니까.
- **리베이스 뒤 병합** — X 가 main 끝 위로 복제되어 X' 가 되고, 이어 Y 가 X' 위로 Y' 가 된다. 다시 놓는 것은
  스냅숏이 아니라 **부모와의 차이**다 — "단추 추가" 라는 고침을 새 바닥 위에 다시 얹는다. 변경은 같아도 부모가
  달라져 해시가 새로 셈해진다(m=1 에서 X' `7c3d66c` · Y' `b95abd3`, m=2 에서 `82eb697` · `07535eb`). 오른쪽
  작은 판이 해시에 들어가는 줄을 보여 준다 — 그어진 `parent` 줄이 옛 부모, 그 아래가 새 부모다. 그 뒤 feature
  이름표가 Y' 로 떠나면 옛 X · Y 는 어느 이름에서도 닿지 않게 되어 흐려진 채 제자리에 남는다. 마지막으로 main
  이름표가 새 커밋을 만들지 않고 X' · Y' 두 칸을 건너 Y' 에 선다(fast-forward). 병합이 늘 빨리 감기라 병합
  커밋은 생기지 않는다.

main 이 앞서 가지 않았으면(m=0) 갈라진 자리가 곧 main 끝이다. main 끝이 feature 끝의 조상이므로 두 길 모두
새 커밋 없이 main 이름표만 B 에서 Y 로 두 칸 건넌다 — 리베이스는 바닥이 이미 main 끝이라 다시 쓸 것이 없다.

### 계기

| 길 | m | 새 커밋 | 병합 커밋 | 해시가 바뀐 복제 | 이름 없이 남은 옛 커밋 | main 이름표가 건넌 칸 | 전체 커밋 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 병합 | 0 | 0 | 0 | 0 | 0 | 2 | 4 |
| 병합 | 1 | 1 | 1 | 0 | 0 | 0 | 6 |
| 병합 | 2 | 1 | 1 | 0 | 0 | 0 | 7 |
| 리베이스 뒤 병합 | 0 | 0 | 0 | 0 | 0 | 2 | 4 |
| 리베이스 뒤 병합 | 1 | 2 | 0 | 2 | 2 | 2 | 7 |
| 리베이스 뒤 병합 | 2 | 2 | 0 | 2 | 2 | 2 | 8 |

"건넌 칸" 은 새 커밋을 만들지 않고 main 이름표가 지나간 커밋 수다. 병합 커밋 위로 한 칸 오르는 것은 새 커밋이
생겨서 옮긴 것이라 세지 않는다. 계기는 판마다 0 에서 다시 센다. m=1 과 m=2 는 계기가 같고, 갈라진 자리까지
main 쪽 거리(1 · 2)와 새 해시 값이 다르다.

한 판은 병합이면 네 걸음, 리베이스 뒤 병합이면 여섯 걸음이다(m=0 이면 두 길 모두 세 걸음).

### 모형이 덜어 낸 것

- 고침은 늘 충돌 없이 얹힌다. 실제 `git rebase` 는 고침을 하나씩 적용하다 충돌이 나면 멈추고, `git merge` 는
  세 쪽 비교(3-way)로 한 번에 합치다 충돌이 나면 충돌 덩이를 남긴다.
- 이름 없이 남은 커밋은 곧바로 사라지지 않는다. git 에서는 reflog 가 한동안 붙잡고 있어 옛 해시로 되찾을 수
  있고, 그 기간이 지나야 치우기(`git gc`)의 대상이 된다. 이 화면은 그 수만 센다.
- `git merge` 는 main 이 조상이면 기본으로 빨리 감기를 하고(`--no-ff` 를 주면 병합 커밋을 만든다), 이 화면의
  병합 · m=0 칸은 그 기본값을 따른다.
