## 두 사람이 같은 줄을 고치면

세 방향 병합은 조상 파일을 심판으로 세워, 한쪽만 고친 자리는 그 고침을 그대로 받아들인다. 그런데 두 사람이
**같은 줄을 서로 다르게** 고쳤다면 어느 쪽이 맞는지 조상도 말해 주지 못한다. 그때 병합은 무엇을 하는가.

{facet:bothTouchedSameLine}

### 파일 셋

조상(base)은 다섯 줄이다.

```
let limit = 10
let step = 2
function next(n)
    return n + step
show next(1)
```

우리 쪽(ours)은 1 줄을 `let limit = 20` 으로, 4 줄을 `    return n * step` 으로 고쳤다. 그쪽(theirs)은 4 줄만
`    return n - step` 으로 고쳤다.

"손댄 줄" 은 조상의 줄 가운데, 조상과 그쪽 파일을 줄 단위로 견주었을 때 그대로 남은 줄로 짝 지어지지 않은
것이다. 줄은 글자 그대로 견준다 — 앞의 빈칸도 줄의 글자이고, 비슷한 줄을 짝으로 보지 않는다. 달라진 줄은
지운 줄 하나와 넣은 줄 하나로 친다.

### 다섯 걸음

처음 모습(걸음 0)을 넣어 다섯 걸음이다.

0. **처음** — 조상을 가운데에, 우리 쪽을 왼쪽에, 그쪽을 오른쪽에 놓는다.
1. **우리 쪽의 표시** — 우리 쪽이 손댄 조상 줄 1 · 4 위로 우리 쪽의 띠가 왼쪽에서 건너온다.
2. **그쪽의 표시** — 그쪽이 손댄 조상 줄 4 위로 그쪽의 띠가 오른쪽에서 건너온다. 4 줄에서 두 띠가 겹친다.
3. **겹침** — 겹친 줄은 4 하나다. 조상 `    return n + step`, 우리 쪽 `    return n * step`, 그쪽 `    return n - step` —
   셋이 모두 다르다. 어느 한쪽이 조상과 같았다면 다른 쪽의 고침을 받으면 되지만, 여기서는 고를 쪽이 없다.
4. **결과** — 병합 결과 9 줄이 한 번에 선다. 겹치지 않은 우리 쪽의 고침(1 줄 `let limit = 20`)은 그대로 들었고,
   겹친 자리에는 두 쪽의 줄이 충돌 표식 사이에 함께 들어갔다. 충돌은 1 이다.

```
let limit = 20
let step = 2
function next(n)
<<<<<<< ours
    return n * step
=======
    return n - step
>>>>>>> theirs
show next(1)
```

병합은 겹친 자리를 스스로 채우지 않는다. 두 쪽을 모두 적어 둔 채 멈추고, 어느 것을 남길지(또는 둘을 섞을지)는
사람에게 넘긴다. 그 풀이는 이 조각의 말이 아니다.

### 전제와 도구

- 덩이 나누기는 git 이 쓰는 세 방향 병합(xdiff)을 단순화한 모형이다. 두 견줌 모두에서 그대로 남은 조상 줄을
  기준으로 파일을 덩이로 나누고, 덩이마다 누가 고쳤는지 판정한다. git 은 붙어 있는 두 고침도 충돌로 보는 등
  세부가 다르다.
- 충돌 표식 `<<<<<<<` · `=======` · `>>>>>>>` 은 git 이 파일에 실제로 적는 모양이다. git 은 표식 뒤에 브랜치
  이름(또는 커밋)을 적는다 — 여기서는 `ours` · `theirs` 로 두었다.
- git 의 기본 꼴은 두 쪽만 적는다. `git config merge.conflictStyle diff3` 로 바꾸면 `|||||||` 아래에 조상 줄까지
  함께 적는다. 이 조각은 기본 꼴을 쓴다.
- 파일의 줄은 어느 언어도 아닌 읽히는 표기다.
