## 넣고 고치고 지운다

표를 바꾸는 문은 셋이다. 셋 다 "표를 고친다" 로 한데 묶이지만 표에 일어나는 일은
서로 다르다. INSERT 는 **줄**을 하나 들이고, UPDATE 는 줄을 그대로 둔 채 **칸 값**만
바꾸며, DELETE 는 **줄**을 뺀다. 줄 수가 바뀌는 것은 INSERT 와 DELETE 뿐이다.

{facet:insertUpdateDelete}

### 걸음 여섯

처음 표 `stock` 에는 줄이 넷 있다 (`1 pen 12` · `2 ink 3` · `3 pad 0` · `4 clip 7`).
문 셋이 위에서부터 하나씩, 끝까지 돈다.

1. `INSERT INTO stock VALUES (5, 'tape', 4);` — `5 tape 4` 가 표 끝에 들어온다.
   영향받은 줄 1, 표는 5 줄.
2. `UPDATE … WHERE qty < 5` 의 판정 — 손대기 전에 다섯 줄을 **모두** 따진다.
   ink(3) · pad(0) · tape(4) 가 걸린다. 방금 들어온 tape 도 걸린다 — 이 문의 WHERE 는
   앞 문이 끝난 **지금의 표**를 보기 때문이다.
3. UPDATE 적용 — 걸린 세 줄의 `qty` 칸이 **한꺼번에** 바뀐다 (3→13 · 0→10 · 4→14).
   `qty + 10` 은 고치기 전 값으로 셈한다. 줄은 제자리에 있고 표는 여전히 5 줄이다.
   영향받은 줄 3.
4. `DELETE … WHERE qty > 12` 의 판정 — ink(13) 와 tape(14) 가 걸린다. pen 은 12 라
   걸리지 않는다. `>` 는 엄격해서 같은 값은 넘지 않은 것이다. 앞의 UPDATE 가 아니었다면
   ink 와 tape 는 여기서 걸리지 않았다.
5. DELETE 적용 — 걸린 두 줄이 한꺼번에 표 밖으로 빠지고 남은 줄이 틈을 메운다.
   영향받은 줄 2, 표는 3 줄 (`1 pen 12` · `3 pad 10` · `4 clip 7`).

줄 수는 4 → 5 → 5 → 3 으로 간다.

### 먼저 전부 따지고, 한꺼번에

UPDATE 와 DELETE 는 줄 하나를 따지고 곧바로 고치기를 되풀이하지 않는다.
**어느 줄이 걸리는지를 먼저 모두 정하고**, 걸린 줄 전부에 한 번에 일어난다. 그래서
한 문 안에서 앞 줄을 고친 결과가 뒷 줄의 판정을 바꾸지 않는다. 문 하나가 끝나고 나서야
다음 문이 그 결과를 본다.

"영향받은 줄" 은 데이터베이스가 문마다 돌려주는 수(affected rows)다. 걸린 줄이 없으면
문은 오류 없이 0 을 돌려준다 — WHERE 에 아무것도 걸리지 않는 UPDATE 는 실패가 아니다.

### 전제

화면의 문은 SQL 그대로다. 표와 값은 예로 정한 것이다. ORDER BY 가 없으면 표의 줄
차례는 약속되지 않는다 — 여기서는 처음 표의 차례로 보였고 새 줄은 끝에 붙였다.
실제 데이터베이스는 새 줄을 어디에 두든 상관없고, 빠진 줄의 자리를 나중에 다른 줄이
채울 수도 있다.
