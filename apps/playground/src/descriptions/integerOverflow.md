
## 그릇이 먼저 정해져 있다

수를 담는 자리는 크기가 미리 정해져 있다. 부호 있는 8비트는 −128 부터 127 까지,
32비트는 −2,147,483,648 부터 2,147,483,647 까지다. 그 너비는 값이 얼마나
커질지와 아무 상관 없이 **먼저** 정해진다.

그래서 자라는 수열은 언젠가 반드시 그릇을 넘는다. 문제는 넘느냐가 아니라
**어디서** 넘느냐다.

{facet:integerOverflow}

## 어디서 넘는지가 그릇 크기에 달렸다

비트 폭을 옮겨 보면 넘치는 자리가 따라 움직인다. 팩토리얼은 4비트에서
`4! = 24` 에, 8비트에서 `6! = 720` 에, 16비트에서 `8! = 40,320` 에,
32비트에서 `13! = 6,227,020,800` 에 넘는다. 피보나치는 같은 네 폭에서 각각
`F6` · `F12` · `F24` · `F47` 이다.

## 그릇을 키우는 것은 답이 아니다

여기서 한 가지가 드러난다. 폭을 4 에서 32 로 올리면 담는 최대값은 7 에서
2,147,483,647 로 **3억 배**가 된다. 그런데 팩토리얼이 버티는 걸음은 3 에서 12 로
**아홉 걸음** 늘 뿐이다.

계기 둘을 나란히 두고 손잡이를 옮겨 보면 그 어긋남이 바로 보인다. 곱셈으로
자라는 수열 앞에서 그릇을 키우는 것은 시간을 조금 버는 일이지 문제를 푸는
일이 아니다. 피보나치가 46 걸음까지 가는 것은 그것이 덧셈으로 자라기
때문이지 32비트가 넉넉해서가 아니다.

## 넘는 순간 값은 말이 안 되는 것이 된다

넘침이 위험한 진짜 까닭은 여기 있다. 값이 **조금 틀리는** 것이 아니다.

8비트에 `6! = 720` 을 담으면 아래 여덟 비트만 남아 `720 mod 256 = 208` 이
되고, 부호 있는 해석으로는 **−48** 이다. 720 을 기대한 자리에 −48 이 온다.
팩토리얼은 음수가 될 수 없는데도 그렇다. 4비트의 `4! = 24` 는 **−8** 이 되고,
32비트의 `13!` 은 62억이 아니라 **1,932,053,504** — 갑자기 작아진 양수가 된다.

크게 틀린 수라면 눈에 띈다. 말이 안 되는 수는 그 다음 셈으로 조용히 흘러간다.

## 아무도 알려 주지 않는다

C · C++ · Java · C# 에서 부호 있는 정수의 넘침은 예외를 던지지 않는다.
경고도, 로그도, 반환값도 없다. 계산은 그냥 이어진다.

그래서 코드 패널의 코드는 **넘침을 재현하지 않는다.** 곱하기 전에 나눗셈으로,
더하기 전에 뺄셈으로 넘칠지를 먼저 묻는다.

```
if (acc > limit / n) { 여기서 넘친다 }
else                 { acc = acc * n }
```

이렇게 하면 중간값이 그릇을 한 번도 넘지 않는다. 넘친 값을 보고 알아채는 길이
없으니, 넘기 전에 묻는 수밖에 없다.
