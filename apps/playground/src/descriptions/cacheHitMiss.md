# 캐시 적중과 실패

앞에 캐시를 둔 서버에서, 같은 요청이 어떤 때는 1 ms 에 끝나고 어떤 때는 21 ms 가 걸리는 까닭은 무엇인가.

{facet:cacheHitMiss}

요청 여덟이 온 차례대로 하나씩 서버를 떠난다. 요청은 먼저 캐시에 닿는다. 찾는 키가 캐시에 있으면
**적중**이다 — 요청은 거기서 돌아서고, 캐시를 한 번 본 1 ms 로 끝난다. 없으면 **실패**다 — 요청은 DB 까지
더 가서 값을 읽어 오고(20 ms), 돌아오는 길에 캐시를 지나며 그 키를 빈 칸에 남긴다. 그래서 실패 한 번은
1 + 20 = 21 ms 다. 이렇게 먼저 캐시를 보고, 없으면 DB 에서 가져와 캐시에 넣는 읽기를 cache-aside 라 부른다.

캐시에 남는 키는 실패 때에만 하나씩 는다. `user:7` · `user:3` · `user:9` 세 키가 처음 올 때만 DB 까지 가고,
같은 키의 두 번째 요청부터는 모두 짧은 길로 돌아선다. 아래 띠에는 요청마다 걸린 ms 가 차례로 이어 붙는다 —
긴 토막 셋과 짧은 토막 다섯이다.

처음 화면을 넣어 걸음 아홉. 끝에 적중 5 · 실패 3 · 누계 68 ms 가 남는다. 실패의 수는 서로 다른 키의 수와 같다.
캐시 없이 여덟 요청이 모두 DB 로 갔다면 8 × 20 = 160 ms 였다.

## 전제

- ms 는 예로 정한 값이다 — 캐시 보기 1 ms, DB 읽기 20 ms. 실제 수는 망과 저장소에 따라 다르다
- 캐시에 값을 넣는 시간은 0 으로 둔다
- 캐시 용량은 키 넷이고 처음엔 비어 있다. 이 요청들로는 키가 셋만 들어 넘치지 않으므로 무엇을 내보낼지(교체)는
  나오지 않는다 — 그것은 LRU 캐시와 가장 덜 쓴 키를 내보내는 이야기다
- 만료(TTL)도 없다 — 시간이 지나 풀리는 캐시는 따로 다룬다
- 값의 내용은 그리지 않는다. 이 조각의 수는 키가 캐시에 있는가 없는가와 걸린 ms 다
