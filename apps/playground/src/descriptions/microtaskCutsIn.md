
# 마이크로태스크가 줄을 가로챈다

코드 여섯 줄이 있다. 둘째 줄은 지연 0 인 타이머를, 셋째~다섯째 줄은 이미 이루어진
약속에 매단 `.then` 사슬 둘을 건다. 타이머 콜백 `B` 는 셋 중 가장 먼저 줄에 서는데,
정작 가장 나중에 불린다.

{facet:microtaskCutsIn}

## 태스크 줄과 마이크로태스크 줄은 서로 다른 줄이다

`console.log('A')` 가 곧바로 찍히고, `setTimeout(…, 0)` 이 태스크 줄에 `B` 를 세운다.
이어서 `Promise.resolve().then(C).then(D)` 사슬이 걸린다. `Promise.resolve()` 는 이미
이루어진 약속이라 첫 콜백 `C` 는 곧장 마이크로태스크 줄에 선다. 둘째 콜백 `D` 는 줄에
서지 않는다 — `C` 의 약속에 매달려 기다릴 뿐이다. 마지막으로 `console.log('E')` 가
찍혀 스크립트가 끝난다. 여기까지 출력은 A E, 태스크 줄은 [B], 마이크로태스크 줄은
[C] 다.

## 스택이 비면 마이크로태스크 줄부터, 그것도 통째로

스크립트가 끝나 스택이 비면 다음 태스크로 건너뛰기 전에 **마이크로태스크 줄이 빌
때까지** 먼저 돈다. `C` 가 실행되며 출력에 C 가 더해지고, 그 순간 `C` 의 약속이 풀려
`D` 가 마이크로태스크 줄 끝에 **새로** 선다 — `D` 는 `B` 보다 한참 뒤에 걸렸는데도
줄이 도는 도중에 서서 함께 비워진다. `D` 마저 실행되어 마이크로태스크 줄이 완전히
빈 뒤에야 태스크 줄의 `B` 가 꺼내진다.

그래서 출력은 A · E · C · D · B 순서로 자란다. `B` 가 태스크 줄에 선 것은 걸음
둘(줄 2)인데 실제로 불린 것은 걸음 일곱이고, 그 사이 마이크로태스크 둘(C · D)이
앞질러 갔다.

## 이 그림이 세운 전제

- 태스크 줄은 하나로 두었다(FIFO). 실제 브라우저는 줄이 여럿이고 우선순위가 있는데,
  이 모형은 그것을 단순화했다.
- `setTimeout(…, 0)` 은 등록하는 걸음에 곧바로 태스크 줄에 선다고 보았다. 표준의
  최소 지연(중첩 5 단계를 넘으면 붙는 4 ms)은 이 코드에 걸리지 않는다.
  실제 브라우저는 이 자리에서 조금 늦게 설 수 있지만 차례(A E C D B)는 같다.
  브라우저 API 호출 자체(`setTimeout` 등록, `.then` 등록, `console.log`)는 0 ms 로
  두고 시각은 아예 그리지 않았다 — 이 조각의 주장은 **차례**이지 걸린 시간이 아니다.
  같은 소재에서 시각(ms)까지 재는 것은 이웃 조각 timer-is-a-floor 의 몫이다.
  렌더(화면 그리기) 기회도 그리지 않는다 — 그것은 microtask-starvation ·
  yield-to-render 의 몫이다.
