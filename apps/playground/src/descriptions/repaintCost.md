## 어디서부터 다시 도는가

브라우저는 화면을 한 번에 그리지 않는다. 스타일을 다시 셈하고(style), 자리와 크기를 다시 재고(layout),
칠하고(paint), 마지막으로 층들을 겹쳐 한 장으로 합친다(composite). 무엇을 바꾸든 이 네 단계를 처음부터
다 도는 것은 아니다 — 바뀐 속성이 **어디서부터** 다시 돌게 하는지가 갈린다.

{facet:repaintCost}

### 속성마다 사슬의 길이가 다르다

`display` 를 바꿔 요소를 렌더 트리에서 통째로 빼거나 넣으면 자리와 크기가 다시 셈해져야 하므로 layout부터
다시 돈다. `height` 처럼 크기 자체를 바꾸는 것도 마찬가지다. 반면 `color` 는 자리에 아무 영향이 없으니
paint 부터만 다시 돌면 되고, `transform` 은 좌표계만 바꾸는 합성 전용 속성이라 원래는 paint 조차 건드릴
필요가 없다.

### 층에 떼어 두면 무엇이 달라지는가

`will-change: transform` 으로 요소를 제 층에 떼어 두면, 그 층은 이미 칠해진 채로 따로 있다. `transform`
으로 그 요소를 옮기는 것은 합성 단계에서 층의 위치만 바꾸는 일이라 다시 칠하기가 **0** 으로 떨어진다. 그런데
`height` 처럼 layout 자체가 도는 바뀜은 층을 나눠 둬도 피할 수 없다 — 레이아웃이 바뀌면 그 아래 흐름 전체가
다시 재이므로, 층 분리는 애초에 layout 을 막는 장치가 아니다.

### 이 예에서

문서 흐름 위에서 아래로 `header · intro · card(card-title · card-text 를 담은) · list · footer` 다섯이
쌓여 있고, 절대 위치 `badge` 가 `card` 와 `list` 에 걸쳐 있다. `property` 손잡이로 `display → height →
color → transform` 순서로 속성을 바꾸면 도는 단계 표시등이 하나씩 꺼지고, 다시 칠해진 요소가 빛나는 수가
줄어든다. `cardLayer` 손잡이로 `card` 를 page 와 함께 두거나 제 층에 떼면, 같은 `transform` 이라도 다시
칠하기가 5 에서 0 으로 떨어지는 것을 볼 수 있다 — 다만 `height` 는 떼어 둬도 다시 칠하기가 그대로다.

### 전제

이 그림은 CSS 상속·우선순위·`!important` 를 다루지 않는다(그 다툼은 `cascade-priority` 의 몫이다).
문서 전체가 아니라 이 다섯 요소만 있는 것으로 가정했고, 무효화의 단위를 실제 브라우저의 더러워진
사각형 영역이 아니라 **겹친 요소 하나** 로 세었다. 시간(ms)이나 프레임 경계는 재지 않는다 — 셈하는 것은
언제나 개수다.
