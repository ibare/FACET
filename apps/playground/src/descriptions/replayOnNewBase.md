## 리베이스한 커밋은 왜 다른 커밋인가

`git rebase main` 을 하고 나면 `feature` 의 커밋들이 `main` 끝으로 "옮겨 간" 것처럼 보인다.
하지만 커밋은 옮겨지지 않는다. **같은 고침을 새 바닥 위에 새로 만든다.** 새로 만든 커밋은
부모가 다르고, 부모가 다르면 해시가 다르다 — 그래서 다른 커밋이다.

{facet:replayOnNewBase}

### 걸음 다섯 (처음 화면 포함)

| 걸음 | 일어나는 일 |
|---|---|
| 0 | 처음 — `main` → D, `feature` → Y |
| 1 | 다시 놓을 커밋을 고른다 — `feature` 에서 닿고 `main` 에서 닿지 않는 것, 오래된 것부터: X Y |
| 2 | X 를 D 위에 X' 로 다시 만든다 — 부모 D(`26d49cf`), 해시 `8660ebd` → `82eb697` |
| 3 | Y 를 X' 위에 Y' 로 다시 만든다 — 부모 X'(`82eb697`), 해시 `6bd2bb2` → `07535eb` |
| 4 | `feature` 이름표가 Y 에서 Y' 로 옮겨 간다 |

끝나면 커밋은 여덟이다. 새로 생긴 커밋이 둘이고, 옛 해시와 새 해시가 같은 짝은 하나도 없다.
옛 X · Y 는 지워지지 않았다 — 이름표가 떠났을 뿐 제자리에 그대로 있다.

### 두 번째 커밋까지 바뀌는 까닭

Y 의 고침은 X 와 상관이 없는데도 Y' 의 해시가 바뀐다. Y' 의 부모는 Y 의 부모(X)가 아니라 방금
만든 X' 이기 때문이다. 커밋은 부모의 해시를 제 안에 적으므로, 앞 커밋 하나가 바뀌면 그 뒤로
다시 놓인 커밋이 줄줄이 새 해시를 얻는다.

### 병합이었다면

같은 두 줄기를 `git merge` 로 합쳤다면 부모가 둘(D · Y)인 병합 커밋 하나가 새로 생기고, X · Y 는
그대로 남아 해시도 그대로다. 이력이 갈라졌다 만난 모양으로 남는다. 리베이스는 그 대신 이력을
한 줄로 펴고, 그 값으로 커밋의 이름을 바꾼다.

이 차이가 실무의 규칙 하나를 낳는다. 이미 다른 사람과 나눈 브랜치를 리베이스하면, 상대가 가진
X · Y 와 내가 가진 X' · Y' 는 같은 고침을 담은 **서로 다른 커밋**이 된다. 그래서 리베이스한
브랜치를 다시 올릴 때는 `git push` 가 거절되고 강제로 밀어야 한다.

### 이 그림이 딛고 선 전제

- **해시는 장난감이다.** 실제 git 은 커밋 해시(SHA-1, 또는 SHA-256 저장소)에 트리 · 부모 · 저자 ·
  커미터 · 시각 · 메시지를 모두 넣는다. 이 그림은 변경 식별자와 부모 해시만 넣어 FNV-1a 32 비트로
  셈하고 앞 일곱 자리를 보인다. 넣는 것이 적어도 "부모가 바뀌면 해시가 바뀐다" 는 실제와 같다.
- **고침은 늘 깨끗이 얹힌다고 둔다.** 파일 줄과 충돌은 그리지 않는다.
- **옛 커밋을 치우는 장면은 없다.** 이름이 없어진 커밋은 git 이 reflog 에 한동안 적어 두고,
  그 유예가 지난 뒤에야 가비지 컬렉션이 치운다. 그 이야기는 이 그림 밖이다.
