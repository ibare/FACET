## OK 는 언제 참이 되는가

데이터베이스가 커밋에 "OK" 라고 답하면, 그 트랜잭션을 맡긴 쪽은 일이 끝났다고 믿고 다음으로 간다. 그런데
바로 그 순간 전원이 나가면 어떻게 될까. 메모리에 있던 것은 전부 사라지고 디스크에 있던 것만 남는다. OK 를
받은 트랜잭션이 다시 켠 뒤에도 남아 있으려면, OK 를 주기 전에 무엇이 디스크에 있어야 할까.

{facet:acid}

### 네 트랜잭션, 열두 사건

줄 a · b · c · d 가 모두 100 으로 시작한다. 트랜잭션 넷이 차례로 돈을 옮긴다 — T1 은 a 에서 b 로 10,
T2 는 b 에서 c 로 20, T3 은 c 에서 d 로 30, T4 는 d 에서 a 로 40. 트랜잭션마다 쓰기 둘(보내는 줄에서 빼기,
받는 줄에 더하기)과 커밋 하나가 있어 사건은 열둘이고, 사건 하나가 틱 하나다. 로그 기록의 번호(LSN)도
틱과 같다.

쓰기는 두 곳만 바꾼다. 로그 버퍼에 `<T1, a, 100, 90>` 같은 기록이 붙고, 버퍼 풀(메모리에 올린 데이터)의
값이 바뀐다. 커밋은 로그 버퍼에 `<T1, commit>` 을 붙인다. 로그 버퍼와 버퍼 풀은 메모리에, 로그 파일과
데이터 파일은 디스크에 있다. 이 모형에는 체크포인트가 없어서 데이터 파일은 끊기기 전까지 한 번도 바뀌지
않는다 — 끊긴 뒤 데이터 파일에 서는 값은 모두 로그 파일에서 다시 한 것이다.

### 커밋 방식 셋

손잡이 **커밋 방식**이 OK 를 로그 내림의 앞에 둘지 뒤에 둘지를 고른다. 내림은 로그 버퍼를 **전부** 로그
파일로 옮기는 일이다.

- **내린 뒤 OK** — 커밋 기록을 붙이자마자 로그 버퍼를 내리고, 그다음에 OK 를 준다. 커밋마다 한 번 내린다.
- **모아 내림** — 커밋 기록만 붙이고 OK 를 미룬다. 5 틱마다(틱 5 · 10) 한 번 내리고, 그때 커밋 기록이 로그
  파일에 든 트랜잭션에게 한꺼번에 OK 를 준다. 화면에서 OK 표지가 커밋 칸에서 다음 내림 칸으로 미끄러진다.
- **OK 먼저** — 커밋 기록을 붙이자마자 OK 를 준다. 내림은 모아 내림과 같이 5 틱마다 한다.

실제 엔진에서 앞의 둘은 여러 커밋을 한 번의 디스크 쓰기로 묶는 그룹 커밋에 가깝고, 마지막은 PostgreSQL 의
`synchronous_commit = off` 처럼 지속성을 조금 내주고 빠른 답을 얻는 설정에 가깝다. 5 틱이라는 주기는 이
예로 정한 값이다.

### 끊고 다시 켜기

손잡이 **끊는 틱**은 몇 번째 틱을 마친 뒤 끊을지를 고른다 (4 · 6 · 9 · 11). 끊기면 메모리가 통째로
사라진다. 다시 켜면 로그 파일을 LSN 차례로 읽어, 로그 파일에 **커밋 기록이 있는** 트랜잭션의 쓰기만 새 값으로
데이터 파일에 쓴다. 커밋 기록이 없는 트랜잭션은 쓰기 기록이 로그 파일에 있어도 통째로 건너뛴다 — 화면에서
그 트랜잭션의 로그 파일 칸에 줄이 그어지고, 데이터 파일 값은 그대로다. 기본 칸(OK 먼저 · 끊는 틱 9)에서 T2 의
쓰기 둘 `<T2, b, 110, 90>` · `<T2, c, 100, 120>` 은 로그 파일에 있지만 `<T2, commit>` 이 없어 둘 다 건너뛰고,
b 는 T1 이 남긴 110, c 는 처음의 100 으로 남는다. 쓰기 둘 가운데 하나만 서는 일은 없다. 이것이 원자성이다.

한 판의 걸음은 처음 모습(걸음 0) · 틱마다 하나 · 끊김 · 다시 켜기(로그 파일에 나타난 트랜잭션마다 하나)다.
처음 켜지는 칸(OK 먼저 · 끊는 틱 9)은 13 걸음이고, 가장 긴 판은 17 걸음이다. 로그 파일이 빈 판(끊는 틱 4 의
모아 내림 · OK 먼저)은 끊김 걸음이 끝이다.

### 잃은 OK

**잃은 OK**는 OK 를 받았는데 다시 켠 뒤 로그 파일에 커밋 기록이 없는 트랜잭션의 수다. 다시 켜기를 마치면 그런
트랜잭션의 OK 표지가 비어 버린 메모리 띠로 떨어져 나간다.

끊는 틱 9 에서 셋을 견주면 저마다 다른 값을 치른다.

| 커밋 방식 | 로그 내림 | 보낸 OK | 잃은 OK |
| --- | --- | --- | --- |
| 내린 뒤 OK | 3 | 3 | 0 |
| 모아 내림 | 1 | 1 | 0 |
| OK 먼저 | 1 | 3 | 2 |

모아 내림에서 T2 · T3 은 커밋 기록을 붙였지만 다음 내림(틱 10)이 오기 전에 끊겨 OK 를 받지 못했다. 답을 못
받았을 뿐 거짓 OK 는 아니다. OK 먼저는 T2 · T3 에게 이미 OK 를 주었는데, 로그 파일에는 틱 5 까지의 기록만
있다 — T2 의 쓰기 둘은 로그 파일에 있어도 커밋 기록이 없어 건너뛰고, T3 은 로그 파일에 흔적조차 없다.

OK 먼저의 잃은 OK 는 끊는 틱 4 · 6 · 9 · 11 에서 1 · 1 · 2 · 0 이다. 주기 내림이 지나간 뒤 끊기면 0 으로 떨어진다
(틱 11 에서는 틱 10 의 내림이 T3 의 커밋 기록까지 데려갔다). 내린 뒤 OK 는 끊는 틱을 어디 두어도 0 이다 —
끊는 때만 옮겨서는 갈리지 않고, 커밋 방식을 바꿔야 갈린다.

### 코드 패널

코드 패널의 `runCommits` 는 로그를 배열 없이 두 수로 센다 — 로그 버퍼까지 붙은 끝 LSN(`logged`)과 로그
파일까지 내린 끝 LSN(`flushed`). 끊김은 `logged = flushed` 한 줄이다. 누가 OK 를 받았는지(`okAt`)와 누구의
커밋 기록이 로그 파일에 있는지(`committed`)를 채운 뒤 잃은 OK 수를 돌려준다. 화면의 값과 같은 규칙이다.
