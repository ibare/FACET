# 페이지 테이블 찾기

프로그램이 쓰는 주소는 메모리의 실제 자리가 아니다. 운영체제는 프로세스마다 **페이지 표**를 두고, 주소를 쓸 때마다
그 표로 실제 자리를 찾는다. 다만 주소 전체를 표에서 찾지는 않는다. 주소를 둘로 갈라 **앞쪽(페이지 번호)만** 표에서
프레임 번호로 바꾸고, **뒤쪽(오프셋)은 손대지 않은 채** 다시 붙인다.

## 무엇을 보나

- 왼쪽 위는 번역할 가상 주소, 가운데는 페이지 표, 오른쪽 위는 번역을 마친 실제 주소다.
- 주소 하나가 세 걸음으로 간다. 먼저 목록에서 아래 작업대로 내려와 **앞 한 자리와 뒤 세 자리 사이가 벌어진다.**
- 앞쪽만 표의 제 줄로 올라가고, 그 줄을 가로지르며 프레임 번호로 바뀐다. 뒤쪽은 작업대에 그대로 남아 있다.
- 마지막으로 프레임 번호는 표에서 내려오고, 오프셋은 표 밑을 옆으로 건너와 둘이 붙는다.
- 끝 화면의 두 목록을 나란히 보면 세 주소 모두 앞 한 자리만 다르고 뒤 세 자리는 같다.

## 이 예의 값

값은 모두 예로 정한 것이다. 실제 시스템에서 잰 것이 아니다.

- 주소는 16비트(16진 네 자리), 페이지 하나는 4 KiB(= 0x1000 바이트)다. 그래서 맨 앞 16진 한 자리가 페이지 번호,
  뒤 세 자리가 오프셋이다. 실제 주소 = 프레임 번호 × 0x1000 + 오프셋.
- 페이지 표(페이지 → 프레임): 0 → 6 · 1 → 3 · 2 → B · 3 → 1. 네 줄 모두 메모리에 있다 — 표에 없는 페이지를
  만나는 일은 페이지 폴트의 이야기라 여기서는 다루지 않는다.
- 번역할 주소는 이 차례로 `0x2A3C` · `0x0104` · `0x3FF0`.
  - `0x2A3C` → 페이지 2 · 오프셋 0xA3C → 프레임 B → `0xBA3C`
  - `0x0104` → 페이지 0 · 오프셋 0x104 → 프레임 6 → `0x6104`
  - `0x3FF0` → 페이지 3 · 오프셋 0xFF0 → 프레임 1 → `0x1FF0`
- 걸음은 처음 화면을 포함해 열이다 (주소마다 셋).

## 왜 이렇게 나누나

페이지 크기가 2의 거듭제곱이라 주소를 페이지 크기로 나눈 몫과 나머지가 곧 앞 자리와 뒤 자리다. 나눗셈이 필요 없이
자리를 가르기만 하면 된다. 한 페이지 안의 바이트들은 프레임 안에서도 같은 차례로 놓이므로, 오프셋은 바꿀 까닭이 없다.
