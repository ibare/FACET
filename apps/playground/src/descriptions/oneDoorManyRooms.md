## 문 하나, 방 여럿

서비스를 여럿으로 나누면 부르는 쪽이 곤란해진다. 사용자 정보는 이 서비스에, 주문은 저 서비스에, 상품은
또 다른 서비스에 있다. 클라이언트가 그 주소를 모두 알아야 할까. API 게이트웨이는 클라이언트에게 **주소
하나**만 쥐여 준다. 모든 요청은 그 한 입구로 들어오고, 어느 서비스로 갈지는 입구가 고른다.

{facet:oneDoorManyRooms}

### 경로표 한 장

게이트웨이는 요청 경로의 **첫 조각**을 본다. `/users/7` 의 첫 조각은 `/users` 다. 그것을 경로표와 그대로
견주어 같은 줄을 찾는다.

| 첫 조각 | 보낼 곳 |
| --- | --- |
| `/users` | users |
| `/orders` | orders |
| `/catalog` | catalog |
| `/home` | users · orders · catalog |

서비스 셋의 처리 시간은 users 30 ms · orders 50 ms · catalog 20 ms 로 두었다. 모두 예로 정한 값이다.
게이트웨이 자신이 쓰는 시간과 네트워크를 오가는 시간은 0 으로 쳤다. 인증이나 속도 제한처럼 실제
게이트웨이가 함께 하는 일, 같은 서비스의 여러 사본 가운데 하나를 고르는 일은 이 그림에 없다 — 여기서
고르는 것은 **어느 서비스인가**다.

### 요청 넷, 걸음 아홉

요청은 `GET /users/7` · `GET /orders/42` · `GET /home` · `GET /admin/stats` 차례로 오고, 하나가 끝나야 다음이
온다. 처음 화면(걸음 0)을 넣어 걸음은 아홉이다.

1. `/users/7` 은 users 로 가서 30 ms 뒤 `200` 으로 돌아온다.
2. `/orders/42` 는 orders 로 가서 50 ms 뒤 `200` 으로 돌아온다.
3. `/home` 은 경로표에서 서비스 셋을 가리킨다. 게이트웨이는 요청을 **셋으로 갈라 한꺼번에** 보낸다.
4. ~ 6. 셋은 제 속도로 돌아온다. 처리 시간이 짧은 차례라 catalog(20 ms) · users(30 ms) · orders(50 ms)
   순서이고, 게이트웨이의 칸에 모인 수가 1/3 · 2/3 · 3/3 으로 는다.
7. 다 모이면 게이트웨이가 한 응답으로 묶어 `200` 을 돌려준다. 묶은 응답이 나가는 때는 가장 느린 것이
   돌아온 50 ms 다.
8. `/admin/stats` 의 첫 조각 `/admin` 은 경로표에 없다. 게이트웨이가 곧바로 `404` 를 돌려주고, 이 요청은
   어느 서비스에도 닿지 않는다.

### 끝나고 남는 것

클라이언트가 안 주소는 게이트웨이 하나뿐인데, 요청 넷이 서비스에 닿은 부름은 다섯이다 — users 2 · orders 2 ·
catalog 1. `404` 는 하나다.

`/home` 을 셋에게 차례로 물었다면 20 + 30 + 50 = 100 ms 가 걸렸을 것이다. 한꺼번에 보내면 가장 느린 하나를
기다리는 50 ms 로 끝난다. 그 대신 클라이언트는 셋의 답이 하나로 묶인 응답만 받고, 어느 서비스가 먼저
돌아왔는지는 게이트웨이 안에서만 보인다.
