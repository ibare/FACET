# 스크럽 띠 실험 — 조각의 걸음을 펼쳐 놓고 끌 수 있는가

브랜치 `experiment/scrub-timeline`. 2026-09-13.

조각의 컨트롤이 지금은 **다시 보기 + 한 걸음** 둘이다. 이것을 재생 전체를 띠로
펼쳐 놓고 임의의 걸음으로 끄는 방식으로 바꿀 수 있는지 실측했다. 결론부터:
**된다.** 조각 72 종을 재어 **65 종(90%)** 이 코어 변경만으로 그대로 성립했다 —
조각도 projector 도 한 줄 고치지 않았다. 남은 것은 두 갈래이고 둘 다 stage 쪽이다:
되돌림이 불완전한 stage 일곱, 그리고 즉시 모드가 필요한 rAF tween 형. 규범 두 곳도
이 갈래를 아직 모른다.

---

## 1. 무엇이 막고 있었나

조각의 algorithm 은 코루틴이라 뒤로 감기지 않는다. 처음 검토에서는 뒤로 가는 길이
둘뿐이라고 보았다.

- **한 바퀴 더** — 조각의 손짚기 루프가 순환이라, 뒤로 가려면 끝까지 밟고 되감아야
  한다. 왼쪽으로 끌었는데 화면이 오른쪽으로 간다.
- **reset 후 빨리감기** — 화면이 처음으로 튕겼다가 다시 채워진다. 걸음당 애니메이션
  400ms 안팎이라 세 걸음이면 1.2초.

둘 다 수용 불가였다. 그런데 이 판단은 **stage 가 어떻게 그리는지 보지 않고** 내린
것이었다.

## 2. stage 는 두 부류다

| 부류 | 수 | 그리는 법 |
| --- | ---: | --- |
| 속성 세팅형 | 213 / 273 | `opacity`·`fill` 등을 세팅하고 부드러움은 CSS transition 에 맡긴다. 반환값이 없다. |
| rAF tween 형 | 60 / 273 | `animate(ms, draw)` 로 진행률을 직접 그린다. |

다수파인 속성 세팅형에서는 **걸음 i 의 화면 = 걸음 0..i 의 세팅을 순서대로 적용한
결과**다. 그러니 되감고 앞에서부터 다시 먹이면 그 걸음이 되살아나고, 한 프레임 안에
몰아 먹이면 CSS transition 이 **지금 화면에서 목표 화면으로 곧장 보간한다.**
되감았다 채우는 것이 아니라 일곱에서 셋으로 곧장 간다.

## 3. 무엇을 쟀나

### 3-1. 되짚기가 순방향과 같은 화면을 만드는가 (happy-dom, 조각 72 종)

`packages/core/test/scrub-replay.test.ts` — 조각마다 두 벌을 띄운다.

```
A  정상 마운트 → 자동 재생 완주 → onReset() → 로그[0..k] 재적용
B  algorithm 을 no-op 으로 갈아끼워 마운트 → 로그[0..k] 만 적용
```

A 와 B 의 DOM 이 같으면 그 조각은 되짚기가 성립한다.

처음 표본 12 종에서 8 : 4 로 갈렸는데, 넷의 차이가 전부 **화면에 뜻이 없는 것**이었다.

- `opacity="1"` vs 속성 없음 — `<g>` 의 기본 opacity 가 1 이라 같은 그림이다.
  되감은 쪽은 한 번 켰던 자리라 명시로 남고, 순방향 쪽은 아직 안 건드려 없다.
- `fill-opacity="1"` · `stroke-dasharray="none"` — 둘 다 기본값.
- `pafcN-hatch` — stage 가 마운트 횟수를 SVG id 에 넣는다. 두 벌을 띄우는 실험
  하네스가 만든 차이지 스크럽의 차이가 아니다.

이 셋을 걷어내니 12 / 12 완전 일치. 표본을 **72 종**으로 넓히자 그림이 달라졌다.

| 견주는 법 | 같음 |
| --- | ---: |
| 처음 (컨트롤바까지 통째로) | 43 / 72 |
| 컨트롤바를 뺀다 | 44 / 72 |
| **되짚기를 실제 구현과 맞춘다** (`onReset` → `onInit`) | 53 / 72 |
| 숨은 것(`opacity: 0`)을 뺀다 | 61 / 72 |
| 기본값·속성 차례를 뺀다 | **65 / 72 (90%)** |

셋째 줄이 실측의 고비였다. 하네스가 `onReset` 만 부르고 되짚었는데 실제 Timeline 은
`onReset` 다음에 `onInit` 을 부른다 (S-runtime 의 reset 순서). **하네스가 실제
구현과 다른 것을 재고 있었다** — 아홉이 그 한 줄로 갈렸다.

넷째·다섯째는 재는 잣대를 "화면에 뜻이 있는 차이" 로 좁힌 것이다. 숨은 요소의
좌표, `stroke-width="1"` 같은 기본값, 그리는 순서에서 온 속성 차례 — 어느 것도 눈에
보이지 않는다.

남은 **7 종**은 진짜 차이다.

```
bstDegenerate  bubbleAdjacentSwap  chainingBucket  coinFlipHeight
depthDoublesCount  editTableFill  growthOutpaces
```

성격은 하나로 모인다 — **stage 의 되돌림이 그 걸음이 바꾼 것을 다 되돌리지 않는다.**
`bubbleAdjacentSwap` 은 되짚은 뒤 칸에 `7` 이 남았는데 순방향에서는 `2` 다. 지금까지
`onReset` 은 "처음으로 되감기" 에만 쓰였고 그 뒤에 `onInit` 이 다시 그리므로 완전하지
않아도 됐다. 스크럽은 그 완전성을 처음으로 요구한다.

### 3-2. 되짚을 때 중간 상태가 화면에 나오는가 (실제 브라우저)

happy-dom 은 레이아웃도 페인트도 셈하지 않아 여기서 잴 수 없다. Chrome 을 CDP 로
몰아 매 프레임 격자 상태를 적었다 (`apps/playground/scrub.html` + scratchpad 의
`cdp-probe.mjs`).

**뒤로 (5 → 3), 97 프레임 중 상태 변화 2회:**

```
t=5046  painted 0   groups 3
t=5210  painted 10  groups 3
```

`groups` 가 처음부터 3 이다 — 다섯 걸음 상태에서 세 걸음 상태로 **중간 없이** 갔다.
구조적 튐은 없다. `painted` 가 0 에서 10 으로 164ms 걸린 것은 그 stage 의
`paintDiff` 가 행마다 40ms 씩 미뤄 칠하는 자체 연출이다.

**앞으로 (3 → 5):** 24 → 38 → 56 → 66 → 88 → 108 → 126 … 걸음마다 애니메이션이
살아 있다.

### 3-3. 끄는 중에 늘어남이 보이는가

포인터 드래그를 CDP 로 재현했다. 처음에는 `stretchWidth: 0%` — 늘어남이 아예 없었다.
**이 조각의 stage 가 애니메이션을 기다리지 않아 재적용이 순식간에 끝났기 때문**이다.
걸음 간격은 원래 algorithm 의 `ctx.sleep(stepMs)` 가 만드는데, 재적용 경로에는 그것이
없다.

그래서 걸음의 리듬을 Timeline 이 직접 준다 — 이미 애니메이션으로 쓴 시간은 빼고
**모자란 만큼만** 채운다. 채우는 몫은 남은 거리에 반비례해서, 멀리 끌면 빠르게
쫓아오고 목표에 가까워질수록 느긋해진다. 고친 뒤 `stretchWidth: 20%`.

### 3-4. rAF tween 형은 어떤가

걸음이 11 인 `split-and-number` (rAF 형) 로 쟀다. 되짚은 **직후에는 멀쩡한데 1초쯤
뒤에 화면이 무너졌다** — 산점도 라벨이 겹치고 값이 뒤엉켰다. 몰아 먹인 걸음마다
tween 이 하나씩 떠서 같은 요소에 서로 다른 값을 쓴 것이다. 눈으로도 늦게야 잡히는
부류다.

두 가지를 고쳐 해결했다.

1. **즉시 모드** — 되짚는 동안 stage 가 진행률을 그리지 않고 끝 상태로 건너뛴다.
   `animate` 안에 이미 있던 `if (destroyed) { draw(1); … }` 옆에 조건을 하나 더
   보태는 일이다. 돌던 tween 도 그때 거둔다.
2. **순차 `await`** — 처음에는 기다리지 않고 던져 두었는데, 비동기 stage 에서
   걸음들의 **`await` 뒤쪽이 뒤섞여** 앞 걸음이 지울 임시 노드를 뒷 걸음이 이미 그린
   뒤가 되었다. 즉시 모드에서는 타이머도 프레임도 걸리지 않으므로, 기다려도
   마이크로태스크로 끝나 여전히 한 프레임에 수렴한다.

고친 뒤 11 걸음 조각에서 되짚기가 깨끗했다.

## 4. 무엇을 만들었나

| 자리 | 한 일 |
| --- | --- |
| `packages/core/src/runtime/timeline.ts` (신규) | projector 를 감싸 자취를 적고 임의 걸음으로 되짚는다. 앞으로는 걸음마다 리듬을 주고, 뒤로는 즉시 모드로 한 묶음에 건너뛴다. |

**조각과 projector 는 한 줄도 바뀌지 않았다.** 자취를 적는 것도 되짚는 것도 러너
층에서 끝난다. 바뀐 것은 조각의 `controls` 선언 한 줄과, rAF 형 stage 의 즉시 모드
뿐이다.

## 5. 남은 것

### 규범 두 곳이 이 갈래를 모른다

`rule-guard` 감사가 짚었고, **코드를 되돌릴 일이 아니라 규범을 고칠 일**이다.
고치기 전에는 다른 조각으로 퍼뜨리지 않는다.

- **S-piece** — "control-bar 는 `CONTROL_SET.piece` 다" 가 문면 그대로다. 띠 갈래를
  추가해야 하고, 그때 "띠를 단 조각은 algorithm 의 손짚기 루프를 어떻게 하는가" 도
  함께 정해야 한다. 지금은 `waitForInput` / `rewind` 경로가 도달 불능으로 남는다.
- **S-runtime** — "두 입력 채널 직교 분리" 에 세 번째가 생겼다. `onSpeedChange` 는
  선례가 아니다 — 그것은 전송 수단일 뿐 종착지가 `mechanism.onControl('speed')` 라
  채널이 둘로 유지된다. `seek` 은 mechanism 을 아예 지나친다. `seek` 을 정식 control
  액션으로 올려 채널을 둘로 되돌리든, 제3 채널을 명시하든 정해야 한다.

### 되돌림이 불완전한 stage

72 종 중 7. 조각 181 로 미루면 스물 안팎이다. stage 의 `onReset`(또는 `rewind`) 이
그 걸음이 바꾼 것을 다 되돌리게 고치면 된다 — 한 곳씩 봐야 하는 일이고, 고쳤는지는
위 계측을 다시 돌려 확인할 수 있다.

전수(181)는 아직 못 쟀다. 조각을 두 벌씩 띄우는 하네스라 배치 24 에서 멎었고,
12 씩 6 배치(72 종)에 7 분 반이 걸렸다. 전수를 재려면 하네스를 가볍게 하거나
나눠 돌려야 한다.

### rAF 형 60개

즉시 모드를 넣어야 한다. `animate` 헬퍼 한 곳에 조건 하나와 `setInstant` 하나라
기계적이지만, 60 곳이다. 지금은 `split-and-number` 하나만 했다. 넣지 않은 조각은
되짚기 1초 뒤에 화면이 무너진다 — 눈으로 늦게 잡히는 부류라 퍼뜨리기 전에 해야 한다.

### 띠가 값어치 있는 길이인가

조각의 걸음은 5 ~ 20 안쪽이다 (잰 둘은 5 와 11). 참조로 삼은 화면은 37 이었다.
다섯 걸음짜리에서 띠가 "다시 보기 + 한 걸음" 보다 나은지는 별도 판단이 필요하다.
길이 차이를 띠가 흡수하도록 칸이 아니라 이어진 띠로 그렸지만, 그것이 값어치까지
만들어 주지는 않는다.
