# 스크럽 띠 전면 지원 계획 — 조각 181 전부

`tasks/scrub-timeline-experiment.md` 의 실험이 90% 를 확인했다. 나머지를 채우고
새 조각이 자동으로 따라오게 하는 계획이다.

---

## 1. 무엇이 남았나

두 축이 있고, **하나는 실측했고 하나는 아직이다.**

### 축 1 — 되짚은 뒤 화면이 맞는가

stage 의 되돌림(`onReset` / `rewind`)이 그 걸음이 바꾼 것을 다 되돌리는가. 지금까지
`onReset` 은 처음으로 되감을 때만 쓰였고 뒤이어 `onInit` 이 다시 그리므로 완전하지
않아도 됐다. 스크럽이 그 완전성을 처음으로 요구한다.

- **전수 실측 (2026-09-13)**: 조각 **181 중 167 통과 (92%), 14 실패.**
- 실패 예: `bubbleAdjacentSwap` 은 되짚은 뒤 칸에 `7` 이 남는데 순방향에서는 `2` 다.
- 확정 목록:

  ```
  bstDegenerate      bubbleAdjacentSwap   chainingBucket        coinFlipHeight
  editTableFill      partitionAroundPivot pickNearestUnsettled  pushPopTop
  recolorThenRotate  requiresSorted       directionOfMostSpread noiseLeftOut
  projectAndLose     hashIntegrityCheck
  ```

### 축 2 — 되짚는 동안 화면이 깨지지 않는가

몰아 먹인 걸음마다 애니메이션이 하나씩 떠서 같은 요소에 서로 다른 값을 쓰면 화면이
엉킨다. **되짚은 직후에는 멀쩡하다가 1 초쯤 뒤에 무너지므로** 눈으로 훑어서는 못
가른다. 즉시 모드가 필요하다.

- **정적 집계**: projector 가 stage 를 기다리는 조각 **84**. 안 기다리는 97 은
  되짚기가 곧바로 끝나 즉시 모드가 필요 없다.
- **실측은 1 건뿐이다** (`split-and-number`). 나머지 83 은 "같은 구조라 같은 문제가
  있을 것" 이라는 추정이다. **이 축을 전수로 재는 것이 0 단계다.**

### 두 축의 관계

겹친다. 손봐야 하는 조각은 두 집합의 합집합이다. 축 1 은 14 로 확정됐고 축 2 는
측정 중이다.

## 2. 손대는 규모를 줄이는 설계

지금 구현은 stage 가 `setInstant` 메서드를 **반환 객체에** 노출한다. 그 자리를 찾는
것이 codemod 의 가장 위험한 대목이다 — 실제로 `split-and-number` 에서 `return {` 의
첫 매치가 다른 함수의 것이라 한 번 어긋났다.

**통로를 `ViewMountParams` 로 옮긴다.**

```ts
// views/types.ts
/** 되짚는 중인가 — stage 의 애니메이션 헬퍼가 본다. 러너가 넣는다. */
isInstant?: () => boolean;
```

그러면 stage 의 변경이 **반환 객체를 건드리지 않고 두 곳으로 줄어든다.**

```ts
const isInstant = params.isInstant ?? (() => false);   // ① mount 첫머리
…
if (destroyed || isInstant()) { apply(1); return resolve(); }   // ② 헬퍼 첫 줄
```

실현성을 실측했다.

| | |
| --- | ---: |
| mount 둘째 인자가 `params` 인 조각 | **148 / 181** |
| 헬퍼 첫머리가 `if (destroyed)` 인 조각 | **85 / 111** |

둘 다 다수파라 정규식 변환이 선다. 빗나가는 것은 손으로 한다.

### 버린 선택지

- **전역 타이머 패치** — 되짚는 동안 `setTimeout` / `requestAnimationFrame` 을
  즉시 실행으로 바꿔치기하면 stage 를 한 줄도 안 고쳐도 된다. **버린다.** 타이머는
  전역이라 같은 글에 박힌 다른 조각의 애니메이션까지 즉시 끝내고, 호출 스택으로는
  누구의 타이머인지 가릴 수 없다. 조각 여럿이 한 글에 박히는 것이 이 프로젝트의
  전제다.
- **코어 공용 애니메이터로 교체** — 가장 깨끗하고 새 조각이 자동으로 따라오지만,
  84 곳을 헬퍼째 들어내는 일이라 지금 단계에서는 크다. 6 단계 이후의 정리로 미룬다.

## 3. 단계

### 0 단계 — 대상을 확정한다 (선행. 이것 없이는 나머지가 추정이다)

**0-1. 축 1 하네스를 가볍게 하고 전수로 돌린다.** ✅ 끝났다 (181 중 14 실패).

지금 하네스는 조각당 **두 벌**을 띄운다 (A: 되짚은 것 / B: 순방향으로 거기까지 간
것). 그래서 배치 24 에서 멎었고 72 종에 7 분 반이 걸렸다.

한 벌로 줄인다 — **순방향 재생 중 걸음마다 화면의 해시를 적어 두었다가, 완주 후
되짚어 그 걸음으로 가서 해시를 견준다.** B 벌이 사라져 비용이 절반이 되고, 같은
인스턴스라 SVG id 일련번호 같은 하네스 인공물이 아예 생기지 않는다. 화면을 통째로
쥐지 않고 해시만 쥐므로 조각 181 을 재도 메모리가 늘지 않는다 — 어긋난 조각은
따로 다시 돌려 diff 를 본다.

걸린 시간 12 분 반 (배치 12 씩 16 배치). 두 벌 하네스로는 배치 24 에서 멎던 것이
전수를 완주했다.

**0-2. 축 2 를 재는 브라우저 하네스를 만든다.**

happy-dom 은 페인트를 셈하지 않아 이 축을 잴 수 없다. CDP 로 잰다.

> 되짚은 **직후**의 화면과 **1.5 초 뒤**의 화면을 견준다. 다르면 지연 발화가
> 덮어쓴 것이다.

`split-and-number` 에서 본 증상이 정확히 이것이라 판정이 선다. 조각당 자동 재생
완주를 기다려야 하므로 배치로 띄운다.

산출물: 축 2 실패 조각의 **확정 목록** (지금은 84 라는 정적 추정뿐). 84 보다 적을
수 있다 — 기다리는 projector 라도 애니메이션이 짧으면 안 겹친다.

### 1 단계 — 즉시 모드 통로를 `params` 로 옮긴다

- `ViewMountParams.isInstant` 추가.
- 러너가 Timeline 의 플래그를 읽는 함수를 넣는다. 지금의 `setInstant` 메서드 순회는
  걷어낸다.
- `split-and-number` 를 새 통로로 옮겨 본이 되게 한다.

코어 변경이라 작고, 이후 모든 단계가 여기 기댄다.

### 2 단계 — codemod 로 stage 를 일괄 변환한다

0-2 가 확정한 목록에 대해서만 돌린다. 84 를 다 고칠 필요는 없을 수 있다.

- 변환 두 줄 (①②). 반환 객체는 건드리지 않는다.
- **배치 20 씩** 끊어 돌리고 배치마다 `typecheck` + 0-2 하네스로 확인한다.
  한꺼번에 돌리고 나중에 재면 어느 변환이 깨뜨렸는지 못 가린다.
- 정규식이 빗나가는 것(85 기준으로 26)은 손으로. 변종은 `await wait(FRAME_MS)`
  루프형처럼 뼈대가 아예 다른 것들이다.

### 3 단계 — 되돌림이 불완전한 stage 를 고친다

0-1 이 확정한 목록. 원인이 stage 마다 달라 **하나씩 봐야 한다.** codemod 가 안 된다.

고치는 방향은 둘 중 하나다.

- stage 의 `rewind` / `onReset` 이 그 걸음이 바꾼 것을 다 되돌리게 한다.
- 또는 그 stage 의 `onInit` 이 바탕을 온전히 다시 그리게 한다 (S-runtime 이 정한
  reset 순서가 `onReset` → `onInit` 이므로 어느 쪽이든 성립한다).

### 4 단계 — 계측을 통과 바로 올린다

지금 `scrub-replay` 는 셈만 찍고 `differ` 가 나와도 통과한다. 계측 하네스이지
회귀를 막는 검사가 아니다.

- 축 1 검사를 **전수 + 실패 0** 으로 올린다. 0-1 의 경량화가 그 전제다.
- 축 2 는 브라우저가 필요해 CI 에 넣기 무겁다. **수동으로 돌리는 검사**로 두고
  `tasks/` 에 돌리는 법을 적는다. 새 조각을 만들 때 돌린다.

### 5 단계 — 규범을 고친다

**코드를 되돌릴 일이 아니라 규범을 고칠 일**이라는 것이 rule-guard 의 판정이다.
고치기 전에는 다른 조각으로 퍼뜨리지 않는다.

- **S-piece** — "control-bar 는 `CONTROL_SET.piece` 다" 를 띠로 바꾼다. 걸음 수로
  가르지 않으므로 갈래를 늘리는 것이 아니라 **갈아 끼우는** 것이다. 손짚기 루프를
  걷어내는 것(7 단계)도 여기 함께 적는다.
- **S-runtime** — "두 입력 채널 직교 분리" 에 세 번째가 생겼다. `seek` 을 정식
  control 액션으로 올려 채널을 둘로 되돌리거나, 제3 채널을 명시하거나.
  `onEvent` 직접 호출 MUST NOT 도 재생 장치의 존재에 맞춰 다시 쓴다.

### 6 단계 — 전 조각에 적용한다

`CONTROL_SET.piece` → `pieceScrub` 일괄 치환 후 전수 검사. 걸음 수로 가르지 않는다.

### 7 단계 — 죽은 손짚기 루프를 걷어낸다 (분리)

`advance` 를 받는 경로가 아무 데도 닿지 않게 되므로 algorithm 에서 걷어낸다.
자동 재생만 하고 끝나는 꼴이 되어 조각의 algorithm 이 눈에 띄게 단순해진다.

**선행 확인**: 자취를 닫는 신호가 `enterAwaiting` 의 `onComplete(true)` 에서
`runAlgorithm` 끝의 것으로 바뀐다 (위 귀결 2). 조각 하나로 확인한 뒤 퍼뜨린다.

스크럽과 다른 의미 단위라 커밋도 나눈다.

## 4. 정해진 것과, 그 귀결

### 걸음 수와 무관하게 띠로 통일한다 (결정)

길이로 갈라 단추와 병행하는 선택지는 없앤다. 조각 181 전부가 띠를 단다.

**귀결 1 — `advance` 단추가 사라진다.** 그러면 algorithm 의 손짚기 루프
(`waitForInput` → `rewind` → 걸음)가 아무도 부르지 않는 경로가 된다. 조각당 20 줄
남짓, 181 곳이다. 걷어낸다. 다만 **스크럽과는 다른 의미 단위**라 6 단계 뒤로
분리한다 (7 단계).

**귀결 2 — 자취를 닫는 신호가 바뀐다.** 지금 Timeline 은 `onComplete(true)` 로
자취를 닫는데, 그 신호가 `ReactiveMechanism.enterAwaiting` 에서 온다 — 즉
`waitForInput` 이 실제로 기다리기 시작할 때다. 손짚기 루프를 걷어내면 algorithm 이
그냥 끝나므로 `runAlgorithm` 끝의 `hooks.onComplete?.(!cancelled)` 가 대신 온다.
**같은 훅이라 그대로 도는 것으로 보이지만, 7 단계에서 실제로 확인해야 한다.**
확인 전에는 걷어내지 않는다.

### 전수로 잰다 (판단)

표본으로 갈음하고 고치면서 발견하는 길은 택하지 않는다. 축 2 는 되짚은 1 초 뒤에
무너지는 부류라 발견이 늦고, 늦게 발견하면 어느 변환이 깨뜨렸는지 못 가린다.
0 단계의 경량화로 비용을 감당한다.
