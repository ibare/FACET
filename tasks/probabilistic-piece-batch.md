# 확률적 자료구조 조각 배치 — 사양 원본

`tasks/piece-batch-protocol.md` 의 절차를 따른 다섯 번째 배치. 이 문서는 호스트가
에이전트에게 넘긴 사양을 그대로 보존한다 — 나중에 화면과 견주려면 무엇을 시켰는지가
남아 있어야 한다.

## 배치를 정한 근거

카탈로그 `cs-fundamentals / probabilistic-structures` 에 완제품 5 + 조각 10 이
선언되어 있고 **facetId 는 0 건**이었다. 이 배치가 조각 열을 채운다. 완제품 다섯
(블룸 필터 · Count-Min Sketch · HyperLogLog · t-digest · 스킵 리스트) 은 조각이
끝난 뒤 따로 판정한다.

**판정 잣대는 셋이다** (`tasks/ml-supervised-batch.md` 가 원본).

1. **IR 이 여섯 언어로 갈린다.**
2. **사용자 조작이 논증을 진다** — 슬라이더를 옮기는 것 자체가 주장이 된다.
3. **조각들이 따로 말한 것을 한 화면에서 잇는다.**

한때 잣대가 IR 하나였고 `tasks/graph-whole-batch.md` 에 그렇게 적혀 있다. 그 문서로
재고 둘을 버리기로 했다가 사용자가 정정해 셋이 되었다 — `linearRegression` 은
`irs.ts` 가 빈 배열인데 완제품이고, 학습률 슬라이더가 논증을 진다. **문서 둘이
어긋나면 새 것이 이긴다.** 이 배치에서 내가 옛 문서를 골라 다섯 중 셋을 버릴 뻔했다.

소재가 다섯으로 갈려 있어 관성 검출에 유리하다 — 블룸 3 · CMS 2 · HLL 2 ·
스킵 리스트 2 · t-digest 1.

### 미리 걸어 둔 경계

**다섯 조각이 해시를 공유한다** (`severalHashesOneValue` · `cannotUnset` ·
`wrongInOneDirection` · `trustTheSmallest` · `leadingZerosTell`). 전부 "격자에 칸이
켜진다" 로 수렴하면 그것이 관성이다. 그래서 동사를 갈라 주었다 — 갈라진다 /
함께 꺼진다 / 막힌다 / 가라앉는다 / 올라선다.

`wrongInOneDirection` 과 `spaceErrorTradeoff` 는 판정과 균형이라 운동이 없기 쉽다.
페이드로 흐를 위험이 이 배치에서 가장 크다.

## 해시 어휘 — 저장소의 기존 조각과 맞춘다

기존 해시 조각(`hashToBucket` · `chainingBucket` · `openAddressingProbe` ·
`loadFactorRehash`)이 쓰는 어휘를 그대로 잇는다. **같은 것은 같게 그린다**
(S-piece PREFER).

- **자리를 고르는 해시** — Java `String.hashCode` 실측. 자리는 `(h & 0x7FFFFFFF) % n`.
- **해시가 여럿 필요하면** 이중 해싱 `h_i = (h1 + i·h2) mod m` (Kirsch–Mitzenmacher).
  `h1` 은 Java `hashCode`, `h2` 는 FNV-1a 32bit 를 마스크한 뒤 홀수로 만든 값이다.
  홀수로 만드는 까닭은 짝수면 여러 `i` 가 같은 칸을 짚기 때문이다.
- **HLL 만 murmur3 32bit 를 쓴다.** HLL 은 비트가 고르게 퍼지는 해시를 전제하는데
  Java `hashCode` 는 짧고 비슷한 문자열에서 그렇지 않다. 실측으로 갈렸다 —
  같은 키 40 개에서 추정 오차가 Java `hashCode` −97%, FNV-1a −91%, murmur3 −8%.
  이 사실은 `leading-zeros-tell` 과 `average-the-buckets` 의 `description.ts` 에
  한 줄로 밝혀 둔다.

## 데이터 (구조가 1차. 파생값은 알고리즘이 셈한다)

아래 수는 전부 스크립트로 실측했다. **자리·해시값·동전 결과는 1차 데이터**이고,
**켜진 비트 · 최솟값 · 추정치 · 층별 노드 수 · 자취 길이는 대조용**이다 — 알고리즘이
1차 데이터에서 스스로 셈해야 하고, 셈한 값이 대조와 다르면 아래 "대조가 안 맞으면"
을 따른다.

### 블룸 세 조각 — 하나의 필터를 공유한다

비트 배열 m=16, 해시 k=3. 넣는 것은 `fig` · `kiwi` · `mango`.

```
fig     h1=    101380  h2=1105500693   자리 [4, 9, 14]
kiwi    h1=   3292336  h2=1073607833   자리 [0, 9, 2]
mango   h1= 103662530  h2= 242548693   자리 [2, 7, 12]
```

*대조: 최종 비트열 `1010100101001010` — 켜진 자리 [0, 2, 4, 7, 9, 12, 14], 7/16.*

질의 대상과 그 자리:

```
date    자리 [14, 7, 0]    ← 셋 다 켜져 있다
apple   자리 [10, 9, 8]    ← 10 이 꺼져 있다
cherry  자리 [9, 2, 11]    ← 11 이 꺼져 있다
lemon   자리 [3, 4, 5]     ← 3 이 꺼져 있다
```

*대조: `date` 는 넣은 적이 없는데 "있다" 고 답한다(거짓 양성). 나머지 셋은 꺼진
칸을 만나 "없다" 로 끝난다. 넣지 않은 열셋 중 거짓 양성은 `date` 하나뿐이다 —
다만 **그 열셋이 무엇이냐에 달린 수**다. 여기서 잰 열셋은 `apple` `elder` `cherry`
`banana` `date` `grape` `lemon` `melon` `peach` `pear` `plum` `lime` `guava` 다.
목록을 바꾸면 거짓 양성의 수가 달라지므로, 글에 쓰려면 목록을 함께 고정해야 한다.*

*대조: 자리를 함께 쓰는 쌍 — `fig` 와 `kiwi` 가 9 번, `kiwi` 와 `mango` 가 2 번.
`kiwi` 의 세 자리를 끄면 `fig` 와 `mango` 가 함께 사라진다.*

- **`several-hashes-one-value`** — 셋을 넣는 것까지만 보인다. 질의도 지우기도 없다.
- **`wrong-in-one-direction`** — 필터가 다 차 있는 상태에서 질의만 한다.
  `date`(있다고 답함)와 나머지 중 하나 이상(없다)이 대비되어야 한다.
- **`cannot-unset`** — 필터가 다 차 있는 상태에서 `kiwi` 를 지우려 든다.

### `trust-the-smallest` — CMS

깊이 3, 폭 5. 스트림 19 개 — `kiwi` 8 · `mango` 4 · `elder` 3 · `cherry` 2 ·
`banana` 2.

키별 행 자리 (1차 데이터):

```
kiwi    [1, 4, 2]
mango   [0, 3, 1]
elder   [4, 4, 4]
cherry  [0, 3, 1]
banana  [1, 1, 1]
```

*대조: 표는 행0 [6,10,0,0,3] · 행1 [0,2,0,6,11] · 행2 [0,8,8,0,3].
`mango` 와 `cherry` 는 자리가 [0,3,1] 로 같아 값도 [6,6,8] 로 같고, 최솟값 6 을 읽어
각각 2 와 4 부푼다. 나머지 셋은 최솟값이 참값과 같다.
`banana` 의 h2 는 5 의 배수라 `r·h2 ≡ 0 (mod 5)` 이고, 그래서 세 줄이 모두 같은 칸을
짚는다 — 자리가 [1,1,1] 이다.
어느 키도 최솟값이 참값보다 작지 않다 — 그것이 이 구조의 성질이다.*

### `space-error-tradeoff` — CMS

같은 구조를 폭만 바꿔 세 번 짓는다. 스트림은 여섯 키가 각각 네 번씩, 모두 24 개 —
`kiwi` · `mango` · `elder` · `cherry` · `banana` · `date`. 깊이는 3 고정.

*대조: 폭 2(칸 6개) 오차합 56 · 폭 4(칸 12개) 오차합 20 · 폭 8(칸 24개) 오차합 4.
정확히 맞힌 키는 0/6 → 1/6 → 5/6. 참값은 모두 4 다.*

폭 셋을 고른 까닭은 계단이 세 번이면 읽히고 그보다 잦으면 수만 남기 때문이다.

### `leading-zeros-tell` — HLL

키 여덟을 이 순서로 흘린다 — **`kiwi` · `elder` · `cherry` · `banana` · `apple` ·
`mango` · `fig` · `date`.**

**이 순서는 저작 결정이다.** ρ 오름차순으로 세워 눈금이 계단처럼 올라가는 것을
보이려고 정했다. 데이터가 정하는 순서가 아니므로 선언에 적고, 그 사실을
`description.ts` 에 밝힌다 (S-piece — 데이터가 순서를 정하는가, 저작자가 정하는가).

murmur3 이진과 앞자리 0 (1차 데이터):

```
kiwi    10010111101101001110100011000011   앞자리 0 = 0   ρ=1
elder   10001011000100011111010000110011   앞자리 0 = 0   ρ=1
cherry  11111001101001010001000110111010   앞자리 0 = 0   ρ=1
banana  11110101011000100010101110101111   앞자리 0 = 0   ρ=1
apple   01110000000101101110100010010000   앞자리 0 = 1   ρ=2
mango   01011111100010000111110000101001   앞자리 0 = 1   ρ=2
fig     00110111000001010110101100101011   앞자리 0 = 2   ρ=3
date    00101010110100011111001100011011   앞자리 0 = 2   ρ=3
```

*대조: 최대 ρ 가 세 번 갱신된다 — `kiwi` 에서 1, `apple` 에서 2, `fig` 에서 3.
추정은 2³ = 8 이고 참값도 8 이다.*

여기서 맞아떨어지는 것은 이 키 집합의 성질이고 늘 그런 것은 아니다. 그 사실을
글이 밝힌다 — 화면에 각주를 두지 않는다.

### `average-the-buckets` — HLL

키 열여섯 — `host-001` 부터 `host-016` 까지. 버킷 4 개(해시 앞 2비트).

버킷과 ρ (1차 데이터):

```
host-001 버킷 3 ρ=3     host-009 버킷 2 ρ=1
host-002 버킷 0 ρ=2     host-010 버킷 1 ρ=2
host-003 버킷 1 ρ=3     host-011 버킷 0 ρ=1
host-004 버킷 0 ρ=1     host-012 버킷 0 ρ=1
host-005 버킷 0 ρ=5     host-013 버킷 3 ρ=7
host-006 버킷 1 ρ=2     host-014 버킷 0 ρ=1
host-007 버킷 1 ρ=2     host-015 버킷 0 ρ=1
host-008 버킷 3 ρ=1     host-016 버킷 3 ρ=1
```

*대조: 버킷별 최대 ρ 는 [5, 3, 1, 7]. 버킷마다 혼자 답한다면 [32, 8, 2, 128] 로
64 배 흩어진다. 넷을 모으면 16.2 이고 참값은 16 이다. 나누지 않고 하나로 셌다면
`host-013` 의 ρ=7 이 전체를 128 로 끌어올린다.*

이 조각의 논증이 저기 있다 — **튀는 놈 하나가 전체를 망가뜨리는데, 나눠 담으면
그 튐이 한 통에 갇힌다.**

### `crowd-the-tails` — t-digest

압축 계수 δ=12, 점 60 개. 뭉치 경계는 스케일 함수
`k(q) = (δ/2π)·asin(2q−1)` 을 1 씩 끊어 얻는다.

*대조: 뭉치 여섯에 점이 [4, 11, 15, 15, 11, 4] 로 들어간다. 분위 구간은
0~7% · 7~25% · 25~50% · 50~75% · 75~93% · 93~100%.
고르게 나눴다면 뭉치마다 10 개씩이었을 것이고, 꼬리 뭉치가 가운데보다 3.8 배
촘촘하다.*

점 60 개의 값 자체는 조각이 정한다 — 분위수가 보이는 분포면 된다. 위 수는
**뭉치에 몇 개가 들어가는가**에 대한 대조다.

### 스킵 리스트 두 조각 — 하나의 리스트를 공유한다

값 열둘 — 3 · 7 · 12 · 19 · 25 · 31 · 38 · 44 · 50 · 57 · 63 · 70.
높이는 동전을 던져 정했고(앞이면 한 층 더, 최대 4층), 결과를 못박는다.

```
 3 [뒤]        높이 1      38 [앞 뒤]      높이 2
 7 [뒤]        높이 1      44 [앞 앞 뒤]   높이 3
12 [뒤]        높이 1      50 [뒤]         높이 1
19 [뒤]        높이 1      57 [앞 뒤]      높이 2
25 [뒤]        높이 1      63 [앞 뒤]      높이 2
31 [앞 앞 뒤]  높이 3      70 [앞 앞 뒤]   높이 3
```

*대조: 층별 노드 수가 12 · 6 · 3 으로 정확히 반씩 준다. 층 2 는 [31, 44, 70],
층 1 은 [31, 38, 44, 57, 63, 70], 층 0 은 전부. 높이 분포는 1 이 여섯, 2 가 셋,
3 이 셋.*

- **`coin-flip-height`** — 동전을 던져 높이가 쌓이는 것과 그 결과로 층이 반씩
  줄어드는 것까지.
- **`skip-a-layer`** — 다 지어진 리스트에서 **57** 을 찾는다.

  *대조: 자취 네 걸음 — 층 2 에서 31(작다) → 44(작다) → 70(크다, 지나쳤다) →
  층 1 로 내려와 57(찾았다). 한 층짜리 리스트로 훑으면 열 번 본다.*

## 공통 지침

앞선 배치에서 값이 증명된 것들이다. 그래프 2차 배치에서 이 지침을 실었더니
70 검사점 중 재발이 1 건이었다.

- **`CONTROL_SET.piece` 를 쓴다.** `[CONTROL.replay, CONTROL.advance]` 를 펴 적지
  않는다.
- **`waitForInput` 은 받은 것의 종류를 본다** —
  `if ((await ctx.waitForInput()).type !== 'advance') continue;`
- **마운트 직후의 첫 걸음은 문(gate)을 지나지 않는다.** 문을 먼저 두면 `stepMs`
  만큼 빈 화면이 보인 뒤에야 그림이 선다.
- **자동 재생이 끝난 뒤 처음 누르는 `advance` 는 되감고 첫 걸음까지 보인다.**
  되감기만 하고 멈추면 눌러도 반응이 없는 것으로 읽힌다.
- **`destroy()` 가 기다리던 promise 를 푼다.** 타이머·프레임을 거두는 것만으로는
  모자라다. S-piece 의 `waiters` 본을 그대로 쓴다 —
  `packages/core/test/destroy-releases-waiters.test.ts` 가 전수로 검사한다.
- **payload 스키마 주석과 실제 발신을 맞춘다** (C2). `ctx.emit` 의 type 은 리터럴.
- **화면에 쓰는 수 뒤에 조사를 붙이지 않는다.** `'{n} 이 남았다'` 는 n 에 따라
  틀어진다. `'남은 것은 {n}.'` 처럼 민다.
- **사람이 읽는 문자열은 열 언어를 갖춘다** — `en` `ko` `ja` `zh` `ar` `es` `fr`
  `hi` `id` `pt`. `title` · `description` · `messages` 뿐 아니라 컨트롤 라벨도.
  `en:` 을 가진 `{ ... }` 는 전부 `LocaleStr` 이다.
- **`initialData` 를 좁히는 것은 stage 의 `mount`** 다. projector 의 `onInit` 에서
  같은 것을 다시 좁혀 stage 로 밀어 넣지 않는다. 걸음마다 오는 payload 는 이와
  달라서 projector 가 좁혀 넘긴다 (C9).
- **`header` · `metrics` · `layout` 을 두지 않는다.** 캔버스 세로는 stage 가 자기
  파일에 상수로 갖고, 가로는 러너가 `PIECE_CANVAS_W` 로 정하므로 적지 않는다.

### 하지 말 것

- **다른 조각의 구현 파일을 열지 않는다.** `facets/**/*-stage.ts` ·
  `projector.ts` · `algorithm.ts` 를 읽지 않는다. 타입 정의(`packages/core/**`)와
  공개 API 는 읽어도 된다. 격리가 이 배치의 존재 이유다.
- **등록 파일을 건드리지 않는다.** `apps/playground/src/catalog.json`, 카탈로그
  codegen 산출물, 상위 index. 열이 동시에 도는 중이라 충돌한다. 등록은 호스트가
  나중에 일괄로 한다.
- **`pnpm install` 을 돌리지 않는다.** 열이 동시에 `pnpm-lock.yaml` 을 건드린다.
  `pnpm --filter <해당 패키지> typecheck` 만 쓰고, 전수 검사는 호스트가 배치 끝에
  일괄로 돌린다.
- **임시 파일은 스크래치패드에 조각 이름을 붙여 둔다.** 레포 루트에 남기지 않고,
  파일명이 다른 조각과 부딪히지 않게 한다.
- **화면에 뜰 값을 지어내지 않는다.** 해시·비트·ρ·자취를 짐작해 채우지 않는다.
  사양에 없으면 호스트에 되묻는다.

### 대조가 안 맞으면

**다른 길로 한 번 더 셈해 보고, 그래도 안 맞으면 사양이 틀린 것일 수 있으니
어느 쪽이 틀렸다고 보는지 근거와 함께 보고한다.** 대조값은 호스트가 스크립트로
뽑은 것이지만 그 스크립트도 이 배치에서 두 번 틀렸다 — 이중 해싱에서 음수 자리가
나왔고(`cherry` → `[9, 2, -5]`), 그 탓에 CMS 표에 `NaN` 이 실렸다. 사양을 의심하는
것은 허용되는 정도가 아니라 요구된다.

**앞의 넷은 한 뿌리다** — 실측 출력에 없던 파생값을 손으로 옮겨 적었다. 프로토콜이
"사양의 수는 손으로 옮기지 않는다" 고 못박아 둔 자리를 그 프로토콜을 쓴 사람이 어겼다.

**다섯째는 종류가 다르고 더 고약하다.** 실측 스크립트가 사양에 적은 규칙
`(h1 + i·h2) mod m` 과 다르게 곱셈 뒤 다시 마스크를 씌웠다. 2³¹ 이 16·2·4·8 로
나누어떨어져 **블룸과 폭 2·4·8 에서는 차이가 사라지고 m=5 에서만 갈렸다** — 그래서
열 중 하나만 틀렸고 나머지는 멀쩡했다. 조용히 한 곳만 썩는 종류의 오류다.

#### 검산이 검산이 아니었다

`banana` 의 자리를 의심한 에이전트에게 나는 "자리 열은 전부 맞다" 고 답했다. 손으로
다시 셈해 확인했다고 믿었는데, **내가 손으로 재현한 것은 스크립트의 artifact 그
자체**였다. 같은 잘못된 방법으로 두 번 셈한 것은 검산이 아니다.

가른 것은 에이전트가 내민 **산술적 불변량**이었다 — "h2 가 5 의 배수이므로
`r·h2 ≡ 0 (mod 5)`, 따라서 세 줄이 같은 칸을 짚어야 한다." 수를 다시 셈하는 대신
수가 따라야 할 성질을 들이댔고, 그것만이 두 방법을 갈랐다.

### 에이전트가 독립으로 같은 자리를 짚은 것

- **`cannot-unset` 의 C4 위반** — algorithm 과 projector 를 둘 다 `cannotUnset` 으로
  등록해 `register-names` 가 깨졌다. 서로 못 보는 **셋**이 각각 보고했다. 호스트가
  고쳤고(`cannotUnsetProjector`), 저장소 전수에서 이름이 `Projector` 로 안 끝나는
  facet 은 0 건임을 확인했다.

### 지침으로 올릴 것

- **계측과 전수 검사는 호스트가 배치 끝에 일괄로 돌린다.** 열 중 넷이 스스로 돌렸고
  그때마다 남의 미완성 패키지를 물어 `piece-first-advance` 와 `register-names` 가
  흔들렸다(표식 수 126 → 127 → 128). 검출로는 값이 있었지만 — C4 위반이 거기서
  나왔다 — 판정으로는 못 쓴다. 한 에이전트는 같은 이유로 일부러 안 돌렸다.
  **규범에 없어서 4 대 1 로 갈렸다.**
- **사양에 파생값을 적을 때는 그 값이 따라야 할 불변량을 함께 적는다.** 위의 다섯째

- **`mechanismKind` 는 `index.ts` 의 `registerAlgorithm` 옵션**이라고 산출 목록에
  적는다. 열 중 넷이 말없이 고쳤고 하나가 지적했다.
