# 조각을 여러 개 만들 때 — 작업 절차

규칙이 아니라 **작업 방식**이다. 코드를 보고 위반을 판정할 수 없으므로 `rules/`
에 두지 않는다. 조각 자체의 규범은 `rules/specifics/S-piece.md` 이고, 서브에이전트
쪽 제약은 `.claude/agents/piece-builder.md` 에 있다.

## 왜 있는가

배치로 만들면 관성이 생긴다. 두 번 겪었다.

- **발췌 15종** — 전부 폐기했다. 같은 파이프라인에 작은 입력을 넣었더니 축척·라벨·
  움직임이 부모 그대로였다.
- **조각 6종 한 번에** — 관성 넷을 찾아 재작업했다. `text()` 헬퍼가 8/9 바이트
  단위로 같았고, 좌표 골격이 5/9 같았고, 위치 애니메이션이 0건이었다.

반면 **하나씩 만든 처음 셋은 겪지 않았다.**

원인은 둘이다.

1. **앞 조각의 코드를 열어 놓고 시작한다.** 골격을 복사하는 순간 질문이 아니라
   템플릿이 형태를 정한다.
2. **규범 자체가 템플릿이 된다.** `S-piece` 의 형태 조항만 기계적으로 지켜지고
   "형태는 질문이 정한다" 는 무시된다. 같은 관성이 C2 위반까지 아홉 곳에 똑같이
   복제된 적이 있다.

서브에이전트 격리는 1번만 막는다. 2번은 사양을 어떻게 쓰느냐에 달렸다.

## 절차

**배치 경계를 두지 않고 흘려보낸다** (2026-09-18 부터). 까닭과 실측은 아래
"흘려보내기" 절.

1. **서브도메인 하나를 통째로 사양화한다.** 조각 수가 열을 넘어도 한 번에 쓴다.
   비슷한 것끼리 모아야 복제가 눈에 띄고, 앞 결과를 보기 **전에** 다 써 두므로
   앞 조각이 뒷 사양에 스미지 않는다.
2. **사양을 쓴다.** 형태를 적지 않는 것이 요점이다.
3. **화면에 뜰 값을 호스트가 확정한다.** 해시·크기·바이트 수를 계산해 사양에 박는다.
   값 계산이 길면 에이전트 하나에 초안을 맡기고 호스트는 "같은 데이터로 두 사람이
   짜면 같은 수가 나오는가" 만 검토한다 — 호스트 컨텍스트에서 셈을 돌리지 않는다.
4. **`piece-builder` 를 동시에 띄운다 — 칸은 열, 하나가 끝나면 다음을 넣는다.**
   가장 느린 하나가 배치 전체를 붙잡지 않는다. **칸 수는 `state.md` 로 센다** (아래
   "호스트 상태"). 2026-09-18 에 손으로 세다 한 알림에 다섯을 넣어 열넷이 돈 적이 있다.
   **앞 서브도메인을 닫는 동안 비는 칸에는 다음 서브도메인의 조각을 넣는다** — 사양은
   이미 통째로 써 두었으니 막을 것이 없다. 같은 날 서브도메인 사이에서 칸이 28 분 비었다.
   에이전트는 `tasks/piece-contract.md` 를 먼저 읽고, 끝내기 전에
   `node scripts/piece-check.mjs <디렉터리>` 를 오류 0 으로 만든다.
5. **감사는 끝나는 대로 흘려보낸다.** 조각이 끝나면 하나~셋씩 묶어 곧바로 rule-guard 를
   "배치 감사" 로 부른다 (`.claude/agents/rule-guard.md` 의 그 절). 서브도메인 전체를 기다리지
   않는다 — 기다리면 만든 에이전트가 지적을 받을 때까지 논다 (완제품은 평균 47 분 놀았다).
   rule-guard 도 칸 하나를 차지한다.
   **지적은 만든 에이전트에게 돌려보낸다** (`SendMessage`). 호스트가 조각 파일을
   고치지 않는다 — 그 에이전트가 맥락을 쥐고 있고, 조각끼리 독립이라 나란히 고친다.
6. **서브도메인이 끝나면 닫는다.** 감사는 이미 흘려보내며 끝났으니 여기서는 기계적인 것만 한다.
   ```sh
   node scripts/piece-register.mjs facets/<domain>/<name> ...   # 등록 넷 + install + codegen
   pnpm typecheck && pnpm test
   node scripts/piece-inertia.mjs facets/<domain>/{a,b,…}/src/*-stage.ts
   node scripts/scene-audit.mjs --port <포트> --only facet:<id>,…
   ```
   rule-guard 는 5 에서 흘려보내며 이미 돌았다. piece-check 가 기계적으로 잡는 것은
   rule-guard 가 다시 세지 않고, 정규식이 못 보는 자리(헬퍼 함수 안의 발신, 기다림이 없는
   루프, 객체 첫 키가 아닌 `type`)와 의미 판단만 본다 — 목록은 rule-guard 정의의 "배치 감사" 절.
7. **사람에게 확인받는다.** 계측을 통과한 것만 올린다.

## 사양 서식

```
개념      머클 트리
묘사      잎의 해시가 부모로 올라간다
동사      올라간다 — 아래에서 위로. 원본은 남고 복제본이 움직인다
데이터    (호스트가 계산한 실측값)
디렉터리  facets/security/merkle-tree/
패키지    @ffacet/algorithm-merkle-tree
facet id  facet:merkleTree
view id   merkle-tree-stage
걸음 간격  stepMs 700
산출      package.json · tsconfig.json · src/{algorithm,scene,<view id>,
          facet,irs,index}.ts  (여섯 파일) +
          apps/playground/src/descriptions/<facet id 에서 facet: 을 뗀 것>.md
```

에이전트에게 주는 지시문은 **사양 + 공통 안내문**이다. 공통 안내문은 서브도메인마다
하나를 스크래치패드에 두고, 앞서 끝난 조각에서 새로 걸린 함정을 거기 **덧붙인다** —
사양은 고치지 않는다. 계약(파일 구성 · 이름 · 검사)은 `tasks/piece-contract.md` 가
가지므로 안내문에 다시 적지 않는다.

### 첫 배치에서 사양이 모자랐던 것

열 중 열이 같은 자리를 지적했거나 스스로 메웠다. 다음 배치부터는 사양에 넣는다.

- **`irs.ts` 를 산출 목록에서 빠뜨렸다.** S-facet MUST 의 파일 구성에 들어 있어
  열 전부가 스스로 넣었다. 조각은 코드 패널이 없으니 빈 배열이다.
- **`stepMs` 를 주지 않았다.** 열이 460~1200 사이에서 제각각 정했다. 걸음 간격은
  읽을 시간을 주는 저작 결정이라 호스트가 확정해야 한다.
- **view id 규약이 없었다.** 전역 레지스트리라 짧은 이름은 충돌한다. 실제로 하나가
  `shift-stage` 로 잡아 나중에 개명했다. `<디렉터리명>-stage` 로 못박는다.
- **임시 파일 자리를 말하지 않았다.** 스모크 스크립트가 레포 루트에 남거나
  스크래치패드에서 파일명이 부딪혔다. 이름을 조각별로 갈라 쓰게 한다.
- **`pnpm install` 을 각자 돌렸다.** 열이 동시에 `pnpm-lock.yaml` 을 건드렸다.
  typecheck 는 호스트가 배치 끝에 일괄로 돌리는 편이 낫다.

## 호스트가 지킬 것

- **사양에 레이아웃·좌표·색을 적지 않는다.** 적는 순간 호스트가 템플릿이 된다.
  캔버스 폭(`PIECE_CANVAS_W`)은 계약이라 예외다.
- **화면에 뜰 값은 호스트가 계산해 넘긴다.** 에이전트는 값을 지어낸다.
  `hashChain` 에서 해시 뒷자리를 지어내고 주석엔 "전부 실측" 이라 적은 전례가 있다.
- **값과 함께 그 값에 이르는 규약을 준다.** 값이 맞아도 **거기 이르는 길이 여럿이면**
  에이전트는 다른 길로 가서 다른 수를 얻는다. 그때 사양은 한 글자도 틀리지 않았는데
  화면이 사양과 어긋난다.

  2026-09-12 토큰화 배치에서 호스트가 BPE 규약 셋을 통째로 빠뜨렸다. 값은 전부
  실측이었다.

  | 빠진 규약 | 안 지키면 |
  | --- | --- |
  | 낱말 끝 표식을 **독립 기호로** 붙인다 | 26 병합에서 9 가 아니라 **7조각** |
  | 짝 빈도가 같으면 **사전순** 앞선 짝 | 조각 수가 12 가 아니라 **13** |
  | 자르는 것은 어휘가 아니라 **규칙 열을 배운 차례대로 재적용** | 중간 조각이 죽어 어긋남 |

  **서로 못 보는 셋이 각각 다른 자리에서 걸렸다.** 앞 배치들의 사양 결함이 *값이
  틀린 것*(비트 폭의 합, 환산 상수, 고침 횟수)이었던 것과 종류가 다르다. 그쪽은
  표 안의 수끼리 맞춰 보면 드러나는데, 이쪽은 **사양만 읽어서는 드러나지 않는다** —
  만들어 돌려 보고 대조해야 보인다. 검사도 감사도 못 본다.

  가리는 물음: **같은 데이터로 두 사람이 짜면 같은 수가 나오는가.** 동률을 어떻게
  깨는지, 경계 표식을 어디에 다는지, 사전과 규칙 중 무엇이 판단을 지는지 —
  이런 것이 하나라도 열려 있으면 적는다. 열려 있는지 알아내는 가장 싼 방법은
  **호스트의 실측 스크립트가 그 자리에서 무엇을 골랐는지 보는 것**이다. 골랐다면
  그것이 규약이고, 사양에 없으면 빠뜨린 것이다.
- **사양에는 구조를 적고 파생값은 대조용으로만 적는다.** 트리의 L/R 링크, 노드별
  키 목록 같은 구조가 1차 데이터이고, 높이·균형 인수·합계·비교 횟수는 알고리즘이
  거기서 셈해야 한다. 파생값을 1차 데이터로 주면 호스트의 오타가 그대로 화면에
  뜬다 — 3차 배치에서 실제로 두 번 틀렸고 두 번 다 에이전트가 잡았다.
- **"밝혀라" 를 쓸 때는 자리까지 적는다.** 예로 정한 값 · 대용 규약 · 알려진 경향 같은 전제는
  설명 글과 개념 메타가 밝히고 화면은 각주를 두지 않는다 (S-piece). 2026-09-18 AI 배치에서 호스트가
  사양 지시문에 "화면과 설명 글에서 밝혀라" 라고 쓰자 조각 다섯이 상시 각주를 올렸고, 호스트 자신도
  하나를 "상시 캡션이 아니라 괜찮다" 고 넘겼다가 감사에서 되돌렸다.
- **이름은 데이터가 아니라 문안이다.** 사양이 "과목 이름 다섯 — 국어 · 수학 · 영어 ·
  과학 · 역사" 처럼 **사람이 읽는 이름**을 1차 데이터로 주면, 그대로 `initialData` 에
  들어가 **한국어가 열 언어 화면에 박힌다.** 데이터에는 **식별자**(`language` ·
  `math` …)를 두고 이름은 `messages` 의 `label.*` 로 빼야 한다.

  2026-09-11 복잡도 배치에서 에이전트가 스스로 고쳤고 **"다음 배치에서 사람 이름 ·
  항목 이름이 데이터로 들어올 때 같은 자리가 또 나온다" 고 짚었다.** 사양을 쓸 때
  이름이 필요하면 **식별자와 표시 이름을 갈라서 준다.**

  덤으로 번역 판단이 생긴다 — `국어` 는 특정 언어의 이름이 아니라 "그 나라 말 과목"
  이라 en 이 `Language` 가 된다. 그 판단은 에이전트가 하는 것이 낫다.

- **대비 수치는 단위를 통일하고 셈법을 적는다.** 두 방법을 견주는 표를 사양에 적을 때
  **양쪽이 같은 것을 세는지** 확인한다. 수를 나란히 놓는 것만으로 독자는 같은 단위라고
  읽는다.

  2026-09-11 복잡도 배치에서 호스트가 찾기를 **후보 수**(64)로, 확인을 **덧셈 수**(5)로
  적어 표 자체가 거짓 대비였다. 에이전트가 잡아 "들여다본 후보의 수" 로 통일했다 —
  덧셈은 후보 하나를 보는 일 **안에서** 일어나므로 세는 층위가 아니다.

  셈법도 함께 적는다. 같은 수치 배치에서 "몫의 합 = 뺄셈 횟수" 가 셈법에 따라 6 과 7 로
  갈렸다(두 수가 같아지면 멈추는가, 0 까지 빼는가). **수만 적으면 어느 셈법의 수인지
  모른다.**

- **동시에 던진다.** 순차 실행은 호스트를 관성의 새 원천으로 만든다.
- **등록은 호스트가 나중에 일괄로.** 동시 실행 중 카탈로그·index 를 함께 건드리면
  충돌한다.
- **계측을 통과하지 못하면 사람에게 올리기 전에 되돌린다.** 격리는 예방이고 계측은
  검출이라 둘 다 필요하다.

## 흘려보내기 (2026-09-18)

### 왜 바꿨나 — 에이전트가 아니라 배치 사이가 느렸다

조각만 연달아 돌린 배치(2026-09-08 · 09-11 · 09-12)의 기록을 재 보니 한 배치(열)가
**75~100 분**이었고 에이전트가 도는 시간은 그 가운데 **20~27 분**이었다.

| 구간 | 시간 |
| --- | --- |
| 에이전트 병렬 실행 (가장 느린 하나가 길이를 정한다) | 20~27 분. 한 번은 한 명 때문에 119 분 |
| rule-guard 감사 | 10~13 분 |
| 감사 지적을 호스트가 조각 여덟 곳에 손으로 고침 | 10~15 분 |
| 등록 — catalog · bootstrap · install · codegen 을 매번 새 한 줄짜리로 | 5~10 분 |
| 다음 사양과 값 계산 | 나머지 |

에이전트 쪽은 수명의 **60%(약 11 분)가 첫 파일을 쓰기 전 탐색**이었다. 규칙 문서
일곱 · core 파일 열둘 · 테스트 넷을 조각마다 처음부터 읽었고, 읽은 것은 조각이 달라도
같았다. 검증 구간은 토큰의 절반을 썼다 — 자체 검증을 조각마다 임시 파일로 새로 짰다.

### 무엇으로 바꿨나

| 전 | 후 |
| --- | --- |
| 규칙 문서 전문을 조각마다 읽는다 | `tasks/piece-contract.md` 한 장. 규칙 문서는 막힐 때만 |
| 자체 검증을 조각마다 새로 짠다 | `packages/core/test/piece-self-check.test.ts` 한 벌 (`FACET_ONLY` 로 좁힌다) |
| 검사가 무엇인지 테스트를 읽어 알아낸다 | `scripts/piece-check.mjs` 한 명령. 조각 하나에 17 초 안팎 |
| 등록을 배치마다 손으로 | `scripts/piece-register.mjs` |
| 감사 지적을 호스트가 고친다 | 만든 에이전트에게 돌려보낸다 |
| 배치 경계에서 모두 기다린다 | 칸을 정해 흘려보내고, 닫는 일은 서브도메인마다 |
| 사양을 배치마다 | 서브도메인을 통째로 먼저 |

`piece-check` 의 정적 검사는 기존 조각 181 에 돌려 거짓 양성을 걷어 낸 것이다. 그때
**실제 위반이 나왔다** — 발신하는 루프가 첫 발신 전에 취소를 보지 않는 자리 서른여덟
(대부분 도달하지 않는 손짚기 루프), `ctx.emit` 의 type 이 삼항식인 것 하나
(`divisor-pairs-sqrt`), 프리셋을 펼쳐 쓴 컨트롤 하나(`bst-degenerate`). 고치지 않고
두었다 — 새 조각의 기준선으로 쓰고, 기존 조각은 따로 정한다.

`piece-self-check` 는 결함을 일부러 심어 이빨을 확인했다 — `reduce` 의 제자리 수정,
`animate:false` 길의 타이머, destroy 가 기다림을 안 푸는 것, 운동이 남긴 속성. 넷 다
잡혔고 되돌리면 통과한다.

**첫 배치 실측** (2026-09-18, 명령어 파이프라인 여덟 — `tasks/instruction-pipeline-piece-batch.md`):
첫 파일까지 11 분 → **3.8 분**, 조각 하나 17.8 분 → **9.6 분**, 띄운 뒤 닫기까지 **36 분**
(앞 방식 한 주기 75~100 분), 등록 **5 초**. 평균 코드 유사도 **0.08** 로 관성은 오히려

### 어떻게

- **분야 하나(서브도메인이 많으면 둘~셋)를 세션 하나로 닫는다.** 다음 분야는 새 세션에서 연다. 한 세션에서 두
  분야를 닫지 않는다.
- **이어가는 데 필요한 것은 스크래치패드의 `state.md` 한 장에 둔다.** 세션이 compaction 되거나 새로 열려도 이것만
  읽으면 이어진다.

  ```
  # <분야> 배치 상태
  칸 10 · 쓰는 중 N
  | facet | 종류 | 에이전트 id | 상태 | 감사 | 비고 |

  사양: <스크래치패드>/<분야>/specs-*.md   공통 안내문: …/common.md
  닫기: 서브도메인 A 등록 ✓ typecheck ✓ …
  ```

  완료 알림이 올 때마다 이 표의 한 줄을 고치고, 칸이 비었으면 대기 줄 맨 위를 띄운다. **칸 수는 이 표에서 센다.**
- **에이전트 보고 전문을 호스트 컨텍스트로 끌어오지 않는다.** 보고 형식이 짧게 짜여 있고(계약 카드 "보고"),
  호스트는 "사양에서 모자랐던 것" 과 "core 나 규칙에서 걸린 것" 만 배치 기록 초안(스크래치패드)에 옮긴다.
- **호스트는 조각 · 완제품 파일을 읽지 않는다.** 판단이 필요하면 `facet-shot` 의 글자 요약이나 검사기 출력을 본다.

### 세 번째 배치 결과 (2026-09-08)

자료구조 조각 열. BST 셋 · AVL 둘 · 레드-블랙 둘 · B-tree 셋.

| | 1차 (배열·리스트) | 2차 (큐·해시·트리) | **3차 (전부 트리)** | 임계 |
| --- | --- | --- | --- | --- |
| 평균 코드 유사도 | 0.12 | 0.17 | **0.20** | ≤ 0.35 |
| 최고 코드 유사도 | 0.22 | 0.30 | **0.47** | ≤ 0.50 |
| 최고 좌표 겹침 | — | — | **0.38** | ≤ 0.60 |
| 그림 어휘 | 7종 | 7종 | **6종** | ≥ 5종 |
| 운동이 있는 조각 | 10/10 | 10/10 | **10/10** | ≥ 70% |

PASS 지만 최고 유사도가 임계에 붙었다. 배치마다 오른다.

#### 유사도가 오른 것은 소재 때문이다 — 좌표 겹침이 그걸 가른다

최고 쌍(`bst-compare-and-go` ↔ `bst-inorder-sorted`, 0.47)을 열어 보면 둘 다
재귀 이등분으로 트리를 앉힌다.

```
x = (lo + hi) / 2
y = TOP + depth * LEVEL_GAP
```

이진 트리를 고정 폭에 앉히는 정석이라 서로 못 봐도 같은 답에 닿는다. **그 쌍의
좌표 겹침은 0.07 이다** — 셈은 닮았는데 그림은 전혀 안 닮았다.

**두 축을 따로 읽어야 한다.** 코드 유사도만 보면 트리로만 짠 배치는 언젠가 0.50 을
넘고, 그때 그것은 복제가 아니라 소재다. 판정은 이렇게 한다.

| 코드 | 좌표 | 판정 |
| --- | --- | --- |
| 높다 | 낮다 | 소재의 수렴. 통과 |
| 높다 | 높다 | **관성.** 골격을 복사했다 |
| 낮다 | 높다 | 우연이거나 캔버스가 좁다 |

1차·2차는 배열·리스트·해시가 섞여 있어 이 구분이 필요 없었다. 한 계열로만 묶는
배치부터 필요해진다.

#### 호스트가 사양의 수를 두 번 틀렸다

프로토콜은 "화면에 뜰 값은 호스트가 계산해 넘긴다" 고 못박았는데, 그 호스트가 틀렸다.

- `rotate-to-balance` — 균형 인수 표에서 한 자리를 0 이라 적었으나 같은 표의
  높이로 셈하면 −1 이다.
- `node-holds-many` — 데이터의 키는 2+2+2+3 = 아홉인데 산문에 "열 개" 라 적었다.

둘 다 에이전트가 잡았다. **막아 준 것은 검수가 아니라 사양의 짜임이다** — 구조
(트리의 L/R 링크, 노드별 키 목록)를 1차 데이터로 주고 파생값(높이, 균형 인수,
합계, 비교 횟수)은 알고리즘이 셈하게 했다. 두 에이전트 다 구조에서 셈한 값을
화면에 띄우고 표는 대조용으로만 썼다.

**그러니 사양에는 구조를 적고 파생값은 대조용으로만 적는다.** 파생값을 1차 데이터로
주면 호스트의 오타가 그대로 화면에 뜬다.

#### 셋이 독립적으로 같은 자리를 짚었다

1차의 `layout-builder` 조회기 누락(여섯이 재발견)과 같은 모양이 셋 나왔다.

- **빌트인 view 에 캡션 자리가 없다.** 둘이 각각 `tree-layout` 을 검토했다가 같은
  이유로 물러섰다 — 조각은 걸음마다 지금 무슨 일인지 말해야 하는데 그 문장이 같은
  캔버스 안에 있어야 하고, 빌트인에는 그 자리가 없다.
- **팔레트에 도메인 리터럴 색이 없다.** 레드-블랙을 맡은 둘이 각각
  `categorical(2, …)` 이 임의 hue 를 줘서 "검다" 는 라벨과 화면을 어긋나게 한다는
  이유로 배제하고, 똑같이 `danger`/`primary` 로 갔다. 둘 다 다크에서 "검정" 노드가
  밝게 뒤집히는 것을 알면서 감수한다고 적었다.
- **`itemDefault` 위에는 `stateInk` 도 `textInverse` 도 못 쓴다.** 하나가 실측으로
  찾았다 — `itemDefault` 는 양 팔레트에서 배경색과 값이 같아, 어느 쪽을 얹어도 한
  테마에서 글자가 사라진다. `colors.text` 가 맞다. 2차에서 신설한 `stateInk` 가
  **상태 타일 전용**이라는 경계를 스스로 그은 셈이다.

### 계측기를 만들자마자 나온 것

조각 아홉의 재작업 전후를 재보니 이렇다.

```
운동     1/4  →  6/9    고쳐졌다
유사도  0.49  →  0.49   꿈쩍하지 않았다
```

그때의 수정은 운동만 도입하고 **코드 골격에는 닿지 않았다.** 눈으로는 고쳤다고
판단했는데 실측은 아니었다. 계측기가 없었으면 몰랐을 일이다.
